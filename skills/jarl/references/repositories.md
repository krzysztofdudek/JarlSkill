# Packages, leases and several repositories

How a package of issues shares one worker branch and one lease, how a lease shows up in git, how one loop directs work in other repositories, and the rules for workers that run in parallel. Read it when you lease issues, read `branches` or a stale lease, or when an issue names a repository other than the loop's own. The terms are defined in [glossary.md](glossary.md).

## Packages and leases

The unit of work is often a **package**: two to ten small issues that touch neighbouring files, handed to one worker on one branch. That is a first-class shape, not a workaround. `set 163-168 in-progress "<who>" --branch jarl/163-packages --worker <name>` writes one lease on every issue in the call: **Branch:**, **Worker:** and **Since:** (the moment, UTC). `set <ids> in-progress` without the flags still writes **Since:**. A lease records no worktree: git allows a branch in at most one worktree of a repository, so the worktree is found through the branch. `--worktree <path>` is a check on the command line and in the tools and stores nothing: a path that exists must be a worktree of a repository of the issue with the lease's branch checked out, or the call is refused. Leaving in-progress (done, dropped, deferred, open) removes Worker, Since (and a **Worktree:** field a lease holds) and keeps Branch, the record of where the work was done.

- `scope --branch jarl/163-packages` with no id bounds the diff by the union of the **Files** of every issue that records that branch (in progress or done), so the package passes in one call. `scope <id> --branch …` still bounds it by that one issue.
- `branches` prints each branch with the issues on it. A lease's worktree is looked up through git (`git worktree list --porcelain` in each repository the issue names), by the lease's branch, and by the stored **Worktree:** path for a lease that holds one; `status`, `resume` and `branches` all read it the same way. It is in one of five states: here (its directory is on this machine); elsewhere (git lists it locked, with a reason, and its directory is not visible from here, as with a worktree made in a devcontainer); not visible from here (git lists it, but neither it nor its parent directory is on this machine); gone (its directory is missing while the parent directory is here, removed under a live lease); or no worktree holds the branch. Only gone is a problem: a worktree in a container is never reported gone. `branches` shows the state next to the path. It marks a lease **STALE** when the worktree it names is gone, the branch it names is gone (listed as `GONE`), or the lease is at least `--stale-hours` old (default 6) while the branch has no commit that recent. It marks a branch **DONE → delete** when every issue on it is done or dropped (one at least done), its tip is in the base — an ancestor of the base, or else an ancestor of every **Merged:** sha its done issues record (a merge made on another branch) — and its worktree holds nothing uncommitted. A branch whose tip is in no recorded merge (commits after the merge, or a squash merge) reads `DONE (merged by record, branch not in base) — verify`; one whose worktree has uncommitted files reads `DONE (worktree dirty)`, and one whose worktree is listed but cannot be inspected from here (elsewhere, or not visible) reads `DONE (worktree state unknown)` and is never marked for deletion, because its uncommitted changes cannot be counted. A branch matched to another issue only by its `jarl/7-` number, with no **Branch:** behind it, is judged by ancestry to the base alone. `status` lists the same stale leases. A branch marked `DONE → delete` is what `merged` removes by itself when it records the merge; one that is still listed is one `merged` kept, for the reason it named.
- A stale lease is shown for the jarl to act on — ask the worker, re-raise, or set the issues back to `open`. Nothing expires and nothing is taken over automatically: that is Horde's territory.

What a recorded merge does with the worktree and the branch is in [The cleanup a merge makes redundant](merger.md#the-cleanup-a-merge-makes-redundant).

## Code in another repository

A loop can keep its issues in one repository while its workers change another: a repository of plans and notes directing work in the code beside it, or one loop directing several repositories at once. The loop stays where `.jarl/` lives, in either mode, and every role still reaches it with `--root` pointing there. The code side moves to the other repository:

- **The issue names it.** `new --repo <name|path>` writes **Repo:** into the issue; `repo <id> <name|path>` sets it on an issue already filed. `--repo` takes the repository's name (the directory `git clone` gives it), its checkout, a worktree of it or a file inside it, and always reduces it to the repository's main checkout. Where that checkout sits beside the main checkout of the loop (`<parent>/<name>`), **Repo:** stores the name; anywhere else it stores the path, and a note on stderr says why, so two repositories that share a directory name stay apart. An issue whose change spans several repositories names them all as one comma list (`--repo tool,lib` → **Repo:** `tool, lib`); each of its files then starts with the name of the repository it is in (`tool/src/a.mjs, lib/src/a.mjs`), a file with none of the names is in the first one, `next` keeps each (repository, path) pair apart, `scope` on it takes `--repo` to say which repository to read and bounds the diff by the files declared in that one, `branches` and `tips` read all of them, and `report` lists the issue under each. An issue without **Repo:** is read in the loop's own repository.
- **A name holds no path.** It resolves, in one place, to `<parent of the loop's main checkout>/<name>`, the main checkout found through git's common directory, so a loop opened in a linked worktree finds its siblings beside the main checkout. On a machine laid out differently, put a symlink to the checkout beside the loop's checkout. A name that does not resolve is shown with its fix (put the checkout, or a symlink to it, at that place), refused by the commands that act on it (`scope`, `merged`, `repo`, `new --repo`, `import --repo`) and marked by the views. Jarl declares a name once, itself, in `.jarl/repos.md`: its root commits (all of them), its origin as found and its base branch, and no path; `repo --base <name> <branch>` changes the base, and every change of `repo` is a log line. A path is read from the loop's root (the directory holding `.jarl/`), never from wherever the tool is called. Which a value is depends on the loop's record format: in format 1 every value is a path; in format 2 a value that starts with `.` or `/` (or a drive letter) is a path and anything else is a name; what raises the format is in [The format marker](record.md#the-format-marker).
- **Where it is on this machine** is printed, never stored: `show` (and `show --json`, as `where`) prints where each repository written as a name is and the worktree git has on the lease's branch, and `status --by repo` prints where each repository is, its base and whether its checkout is on it (a warning only).
- **Its files carry the repository's name.** Each file in **Files:** starts with that repository's directory name — a name is its own, a path ends in it — and goes on with the path inside it: **Repo:** `tool` → **Files:** `tool/src/a.mjs, tool/CHANGELOG.md`. A reader of the issue sees where each file lives, and `next` reads a file as its repository and its path: `CHANGELOG.md` in two repositories never holds an issue back, two repositories that share a directory name are still told apart by their **Repo:**, and two issues on the same file in one repository still wait for each other. An issue without **Repo:** writes its paths without a name, as in a single-repository loop. One case is decided by rule, not by guess: a repository that has a directory of its own name inside it (repository `app` with `app/x.mjs`). There the prefix is required — `app/app/x.mjs` is `app/x.mjs` inside the repository — and an entry that starts with `app/` but not `app/app/` is a path inside the repository and is never stripped. A repository is one repository however its **Repo:** path is spelled (a symlink, or another case where the file system ignores case), and `--repo` on `scope` reads Files the same way the field does.
- **`scope` reads there.** Commits, files and assertions come from the worker branch in that repository, against its current branch as the base; `--repo <path>` on one call does the same and wins over the field. The repository's name is dropped from each declared file, and the path after it is matched against the branch's changed files.
- **`branches` reads there with `--repo <path>`.** Without it, it lists the loop's own repository only, so at boot run it once per repository the open issues name.
- **The worker, the reviewer and the merger work there.** The worker's worktree and its `jarl/7-slug` branch are cut in that repository from its own feature branch, and that is the branch the brief names; the reviewer diffs there; the merger merges and runs the check in that repository's main checkout. `.jarl/` never enters that repository.
- **`resume` and `tips`** show where that repository's branches stand, beside the loop's own.

## Parallel workers in worktrees

The rules a session with several workers in worktrees runs by; `jarl --help` ends with the same list in short.

- **The default mode keeps the loop out of git.** It lives in the main checkout, and a worktree cannot see it, so every call from a worktree, a worker's or the coordinator's, passes the main checkout as `root`. Several workers writing at once queue on the write lock and lose nothing, and the one `log.md` is shared on purpose: it is the record.
- **In the committed mode the merger alone commits `.jarl/`.** A worker never does, because a worker's commit of the loop would carry a copy that nobody else writes.
- **The coordinator files the issues.** A worker reports what it found, or files with `root` set to the main checkout, so numbers never collide.
- **An issue in progress is held by a worker.** That is the lease: it stays in progress after an approve until the merge is recorded and the issue is set done, `resume` shows it with its worker, branch and start, and `status` counts the issues in flight and lists the stale leases.
- **`list` hides finished and deferred work.** It shows the open and in-progress issues; `--all` shows every status, and `--status`, `--tag`, `--prio` and `--grep` narrow by status, tag, priority and text.
