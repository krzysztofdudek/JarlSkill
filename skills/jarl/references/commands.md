## The tools and their fields

The fields, command by command:

- the flags `--acceptance`, `--changelog`, `--ran` and `--saw` repeat, so their fields are lists, and `ran` and `saw` pair up by position; the list flags (`new`'s `--tags`, `--files`, `--repo`, `--source` and `--after`, `import`'s `--tags`, `--repo` and `--only`, `decide`'s `--settles`) repeat too, and their fields are lists of items. The flag fields: `init` committed, permanent, profile · `new` kind, prio, tier, tags, files, repo, found-by, where, what, why, acceptance, source, after, changelog, template, field, section · `body` title, where, what, why, acceptance, changelog, section, by, append · `import` source, kind, prio, tier, tags, repo, found-by, only, adopt, dry-run, field · `sources` source · `source` by · `after` clear, by · `evidence` ran, saw, file, slot · `retract` by · `field` clear, by · `list` status, kind, tag, prio, grep, match, all · `show` full · `set` branch, worker, model, worktree, handover, header · `tag` by · `prio` by · `files` by · `repo` clear, base, by · `next` limit, all, as · `review` by, model, relayed · `round` findings · `tick` by · `models` by, with, archives · `scope` branch, base, repo · `branches` base, repo, stale-hours · `merged` sha, ci, repo, ran, saw, red, keep · `ask` kind, target, issue, option · `answer` by, option · `resume` log, ready, ci, as · `decide` settles, by, quote, under, supersedes, area, reach, rule · `decisions` live · `goal` set · `status` stale-hours, by, tag, as · `report` found · `queue` repo, base · `changelog` repo · `close` force, batch;
- the argument fields, in the order the usage writes them: `init` goal · `new` title · `body` id · `import` file · `sources` files · `source` id, refs · `after` id, ids · `evidence` ids, text · `retract` id, what, reason · `field` ids, name, value · `show` id · `set` ids, status, why · `merged` ids · `tag` ids, ops · `prio` ids, priority · `files` id, paths · `repo` id, path · `review` ids, verdict, findings · `round` id, what · `tick` id, line · `scope` id · `ask` question · `answer` id, answer · `log` event · `decide` slug, ruling · `archive` slug · `changelog` ids · `mode` mode · `profile` file (`sources`, `tag`, `files`, `source`, `after` and `repo` take a list in their last field: the findings files, the `+a`/`-b` operations, the paths, the references, the ids waited on, the repositories; the `id` of `body`, `source`, `after`, `files`, `repo` and `round` takes one id or a list with ranges, and the call lands on every id or on none; every list field reads its items by the one rule in [Lists](#lists)); the absolute paths are `import`'s `file`, `sources`' `files`, `init`'s `profile` and `profile`'s `file`;
- every tool takes `json` (true answers with what `--json` prints) and `root` (what `--root` is: the checkout that holds `.jarl/`, as an absolute path — a relative or empty one is refused).

The answer is the text the command prints; a note the command prints on stderr comes as a second block. A refusal is an error result with its reason, and nothing was written; a `scope` that found something wrong is an error result too, with its items (the CLI's exit code 2). Jarl has no error document: with `json: true` a refusal's one block is the reason as plain text. A value that starts with `--` is just a value in a field, except an item of a list, which [Lists](#lists) refuses. When a call gave no `root`, the answer names the loop it reached: as a block after the text, or, with `json: true`, in `_meta['jarl/loop']` instead, and the CLI's stderr notes go into `_meta['jarl/warn']` the same way, so a host that parses the one JSON block never has to skip anything.

**Which loop a call reaches:** its `root` field; without it, the server's `JARL_ROOT` environment variable (set it in the server's configuration to pin one loop — as an absolute path: a relative one is refused, for the same reason a relative `root` is, rather than resolved against the server's own working directory); without that, the loop found from the directory the host started the server in — the session's project — the way the CLI finds it from its own working directory: at the root of that checkout, or of its main checkout from a worktree that holds no loop of its own, and never in a subdirectory (a loop kept in one is reached only through `root`, `--root` or `JARL_ROOT`). The server lives as long as the session, not in the worktree a role works in, so every brief says to pass `root` on every call (see [The command line](#the-command-line) for the same rule on the command line).

## The commands

| Command | What it does |
|---|---|
| `init "<goal>" [--committed] [--permanent] [--profile <file>]` | creates `.jarl/` with the goal and a `.gitignore` that keeps the loop out of git; `--profile` checks the profile file against the schema and stores it as `.jarl/profile.json` (see [Profiles](profile.md#profiles)); `--committed` writes a `.gitignore` that ignores only the write lock and temporary files, so the loop is committed with the work; `--permanent` is committed the same way, adds `.jarl/.permanent`, and opens the loop with no feature branch of its own — see [Where the loop lives](record.md#where-the-loop-lives); on the command line it says once when the goal names no `Check` line: the loop then lands on testimony alone, whatever its merges record, until the goal declares one |
| `new "<title>" [--kind k] [--prio 1\|2\|3] [--tier light\|standard\|strong] [--tags a,b] [--files p,q] [--repo <name\|path>] [--found-by who] [--where w] [--what w] [--why w] [--acceptance line]... [--changelog entry]... [--source <dir>#<id>] [--after <ids>] [--template <name>] [--field "<Name>=<value>"]... [--section "<Heading>=<text>"]...` | files an issue under the next free number; `--field` and `--section` (repeat each) write a field and a section the loop's profile declares, a field's default when it is not given and a required one refused when it is missing (see [Profiles](profile.md#profiles)); without `--tier` it records `standard` and says so on stderr, with what each tier is for (see [Which model sits where](models.md#which-model-sits-where)); `--repo` names the repository its code lives in when that is not the loop's own (see [Code in another repository](repositories.md#code-in-another-repository)); `--where`, `--what`, `--why` and `--acceptance` (repeat it, one checkable line each) write the body in the same call, `--changelog` its changelog entry (see [Changelog fragments](worker.md#changelog-fragments)), `--source` names the research finding it comes from, `--after` the issues it waits on; `--template` starts from `.jarl/templates/<name>.md` (see [Templates](jarl.md#templates)); the reply's first line is `filed 7 · file`, then it lists what was parsed (priority, tier, kind, tags, acceptance lines, the length of What and Why) and every field left empty with the command that fills it; a What, Why or section text that holds a matched `<why>…</why>` pair (the name of any field) outside code is refused, because the fields belong in their own parameters; from a linked worktree of a committed loop whose main checkout holds the same loop, `new` refuses and names the main checkout as the root to pass, and from anywhere else the number is the highest over the main checkout and every linked worktree, plus one |
| `body <ids> [--title t] [--where w] [--what w] [--why w] [--acceptance line]... [--changelog entry]... [--section "<Heading>=<text>"]... [--by who] [--append]` | the first of the description commands (`body`, `field`, `tag`, `prio`, `files`, `repo`, `source`, `after`; see [The description and the history](record.md#the-description-and-the-history)): sets or replaces the title (the heading only; the file keeps its name), the **Where:** field, the What, Why, Acceptance and Changelog sections and a section the profile declares (`--section`) of a filed issue, with one log line per part that records what it held before and, when `--by` names someone, who changed it; with `--append` the text is added after what the section holds (a list gains its new items) instead of replacing it, and the title and the Where field cannot be appended to; Evidence is never written here |
| `field <ids> <name> "<value>" [--by who]` · `field <ids> <name> --clear [--by who]` | writes one header field of the description on every issue, each checked as its own command checks it: **Title**, **Priority:**, **Tier:**, **Kind:** (the last three against their values, the profile's for Tier and Kind), **Found by:**, **Tags:**, **Files:**, **Repo:**, **After:**, **Source:** (a list, replaced whole), **Where:**, **Resources:** (the exclusive resources an issue holds while its lease lasts, see [The issue file](record.md#the-issue-file)) or a field the loop's profile declares, checked against its values, with a log line per issue that records what it held before and, when `--by` names someone, who changed it; `--clear` empties an optional field, and Title, Priority, Tier, Kind, Found by and a field the profile requires are never empty; any other name is refused with the names `field` writes and the command that writes that one (`set` for the status and the lease, `merged` for a merge and its CI, `body` for a section, none for the history) |
| `tag <ids> +a -b [--by who]` · `prio <ids> 1\|2\|3 [--by who]` · `files <ids> p,q [--by who]` · `repo <ids> <name\|path>[,<name\|path>...] [--by who]` · `repo <ids> --clear [--by who]` · `repo --base <name> <branch>` | header fields of the description, each change logged with what the field held before and, when `--by` names someone, who changed it; **Repo:** may name several repositories, by name or by path, and `repo --base` changes the base a declared repository is held against (see [Code in another repository](repositories.md#code-in-another-repository)) |
| `after <ids> <after-ids> [--by who]` · `after <ids> --clear [--by who]` | the issues these wait on (**After:**): `next` does not offer one until each of its After issues is done or dropped, and `status` counts it as waiting instead of open or in flight; a chain that would come back to the issue is refused |
| `import <findings.json> [--source <dir>] [--kind k] [--prio p] [--tier t] [--tags a,b] [--repo <name\|path>] [--found-by who] [--only <ids>] [--adopt] [--dry-run] [--field "<Name>=<value>"]...` · `sources [<findings.json>...] [--source <dir>]` · `source <ids> <dir>#<id>,... [--by who]` | research findings into issues, once each, and the coverage view — see [From research to issues](jarl.md#from-research-to-issues) |
| `list [--status s] [--kind k] [--tag t] [--prio p] [--grep re] [--match "<field>=<value>"]... [--all]` | open and in-progress by default, sorted by priority; `--all` lists every status; `--match` keeps the issues whose header field holds the value (any field, a profile's own included; repeat it to require several) |
| `show <id> [--full]` · `status [--stale-hours n] [--by repo\|tag\|kind\|prio\|<field>] [--tag <t>] [--as <who>]` | one issue as the done gate sees it — the header, What, Why, Acceptance and Changelog; every `--ran`/`--saw` row (numbered `[n]` over the whole Evidence section, the number `retract` takes) and every verdict in [the gate's window](profile.md#the-window-of-the-done-gate); every `changes` finding no later approve has answered; one line for each round that came before; last, the exact call that prints everything — `--full` prints the file (rows still numbered), `--json` is complete; under the header, where each repository written as a name is on this machine and the worktree git has on the lease's branch (`--json`: `where`), on stdout only · the loop's goal, when it was opened and when anything last happened, then one line of counts (open, in flight, waiting, done, dropped, deferred, questions, to ratify, merged with CI pending or red), then the landing banner — one line per repository, `k of n merges carry the declared check`, or the testimony mark for a repository that declares no check and while no merge carries the declared check — and, with `--by repo`, the merges of each repository by what they carry (the declared check, not, landed on red), then the choices awaiting ratification, the stale leases, the merges waiting on CI, the waiting issues, the issues in flight with no acceptance line, one line for each issue in flight that says what the record shows and what comes next (`no evidence rows since the start`; `evidence rows recorded, no verdict` — it waits for a reviewer; `changes requested` — back with the worker; `approved and queued` — the merger lands it, then it is set done; `approved by a coordinator only` on an issue that carries code — the merge queue and done refuse that, it waits for a fresh reviewer; `merged, CI not green yet` — record the CI result; `merged` — set it done; derived from the evidence rows and verdicts after the last start or round, never stored, so no status carries it) and, in a committed or permanent loop, how many loop files git has not committed; `--by` adds the five status counts per repository, tag, kind, priority or a field the profile declares (see [Views for dashboards](#views-for-dashboards)); `--tag <t>` computes every part of `status` (the counts, in flight, stale, waiting, CI, the questions that name those issues, the reviews) over the issues carrying that tag only, for a jarl directing one scope of a large loop — the tag is refused when no issue carries it, `--json` has the same shape plus `tag`, and the goal, the loop files not committed and the check state stay the loop's own; all three print one `record:` line for each header field that disagrees with the log (`disagreements` in their `--json`, only when there are any), see [When a header disagrees with the log](record.md#when-a-header-disagrees-with-the-log); `status --as <who>` ends with what `next --as <who>` prints (`as` in `--json`) |
| `archive "<slug>"` | puts the current loop away under `.jarl/archive/<yyyy.mm.dd>-<slug>/` — issues, goal, decisions and log — and leaves the archive, the mode markers (`.gitignore`, `.permanent`) and the templates (`.jarl/templates/`), so the next `init` here opens a new loop in the same mode; open work does not refuse it, but the result and the archived log name it |
| `set <ids> <status> "<why>" [--branch <b>] [--worker <name>] [--model <m>] [--worktree <path>] [--handover] [--header]` | changes status and writes the log line in one move; `in-progress` writes the lease (see [Packages and leases](repositories.md#packages-and-leases)), and the lease holds: an issue another worker or branch holds, and a file or resource another lease holds, are refused (same place); `--handover` hands a leased issue to a new worker or branch, `"<why>"` being why the worker changed; the lease records no worktree: `--worktree` is a check that stores nothing, refusing a path that exists and is not a worktree of a repository of the issue with the lease's branch checked out; `--model` the model the worker was raised on, as the platform names it, `@<effort>` included where the platform has that lever, stored as given (a **Model:** field removed with **Worker:**, and `· model <m>` in the lease's log line, before the worker); in a loop with `Model (<tier>):` lines, a lease without `--model` is noted on stderr, and a `--model` that spells a model the record holds in another way is noted on stderr in any loop (the log keeps each spelling as written); `done` needs at least one `--ran`/`--saw` evidence row (an attachment row counts as one) and a live approve, both inside the gate's window (see [the window of the done gate](profile.md#the-window-of-the-done-gate)), and every slot a profile requires of the issue's kind (see [Attachments](profile.md#attachments)), and the owner's tick of every acceptance line only he ticks (see [The owner's sign-off](profile.md#the-owners-sign-off)); a free-text note never counts on its own, so nothing written at filing time is proof of the work; issues already done stay done, only the next move to done is checked (and it notes on stderr, never refusing, an issue with no acceptance line, with fewer `--ran`/`--saw` rows than acceptance lines, or with a recorded merge whose CI is not green yet), `dropped` and `deferred` need a reason (`deferred` is work that waits, not work that is gone: the default `list` hides it, `list --status deferred` shows it, `status` and `report` count it apart, and `close` says what it leaves waiting) |
| `evidence <ids> "<text>"` \| `evidence <ids> --ran "<command>" --saw "<what it printed>"` \| `evidence <id> --file <path> --slot <name>` | appends a free-text note, or one checkable row per `--ran`/`--saw` pair (repeat the pair for more rows, in one call or several) — `--ran`/`--saw` for what proves the work, free text for what only explains it (rows go to Proof and text to Notes, see [Proof, Notes and the merge record](profile.md#proof-notes-and-the-merge-record)); `--file`/`--slot` records one file as an attachment, a Proof row of its own (see [Attachments](profile.md#attachments)); nothing already recorded is ever replaced; a free-text note that runs long is written whole and noted on stderr (command line only) |
| `retract <id> review --by <who> "<reason>"` · `retract <id> <n> --by <who> "<reason>"` · `retract <id> note-<n> --by <who> "<reason>"` | takes a record back by an appended entry that says who and why: `review` retracts the newest approve not yet retracted, `<n>` the n-th evidence row (the number `show` prints), `note-<n>` the n-th free-text note (the number `show` prints before it); the approve, the row or the note stays, struck through, and `done` and the metrics do not count it; never a `changes` verdict (see [Retracting](profile.md#retracting-a-verdict-or-an-evidence-row)) |
| `next [--limit n] [--all]` | only the open issues ready to start: they share no file with any in-progress one, their **After:** issues are all done or dropped, and no open `stuck` or `stop` question names them — what can run in parallel now; a file is its repository and its path, so the same path in two repositories never holds an issue back; an issue offered with no acceptance line is marked `(no acceptance yet)`, one with no declared files `(no files declared)`. `--all` adds the rest under headers: held by a file another issue holds (and by which issue), held by a resource another issue holds, waiting on **After:** (on which issues), held by an open question (which one). In a loop with `Model (<tier>):` lines each ready row also shows the default model of its tier, read from those lines alone (`--json`: `model: { default }`); `models` is the view that measures models. `--json` rows keep their fields and carry `group`: `ready`, `held-by-file`, `held-by-resource` (an in-progress issue or one offered before it holds a **Resources:** name; `resources` and `heldBy` name them), `waiting-after` or `held-by-question` (`heldBy`, `after` or `questions` name the holder); without `--all` only the `ready` rows are listed, and when none is ready the text says how many are held or waiting |
| `next --as <who> [--all]` | what is on one holder now, each line with the command that moves it (see [What is on whom](#what-is-on-whom)); `<who>` is `owner`, `jarl`, a coordinator or a person by name; at most seven lines, then how many more, `--all` every line and the issues that wait on that holder; `--limit` is refused with it. `--json`: `{ as, rows, total, more, waiting, waitingTotal }`, each row `{ what, holder, says, command, holdsUp }` with `id`, `ask` or `ruling`, the one line for the proofs of code with no verdict `ids` (every issue it lists, `id` the first), a question that asks for a fresh review `reviewing` (the issues it holds), a lease's row `doer` (its worker), an owner line's row `line` (its number) and, on the owner's list, `material` and `check`, `waiting` `[{ id, title, on, via }]`; `note` for a coordinator while the loop has no slices, `scheduler` and `schedulerNote` under an external scheduler |
| `review <ids> approve\|changes --by <reviewer> [--model <m>] [--relayed] "<findings>"` | the reviewer's verdict; `--model` is the model the reviewer was raised on (stored as given; the log line carries `· model <m>` after the standing, and the `## Reviews` entry after the date), and `--relayed` marks a verdict recorded by someone else in the reviewer's name (`· relayed`) — only for a reviewer that cannot be resumed to record its own (see [Which model sits where](models.md#relaying-a-verdict)); in a loop with `Model (<tier>):` lines, a verdict without `--model`, an approve by the model leased on the issue and an approve by a model ranked below the worker's are noted on stderr, never refused; a `--model` that spells a model the record holds in another way is noted on stderr in any loop; the whole findings go under the issue's `## Reviews` section (verdict, reviewer, standing, date, every line) and the log line keeps the first line and a pointer; `changes` needs the word Critical or Important in the findings (naming no severity is refused, and Minor alone cannot bounce a branch: it rides an approve into evidence); every verdict needs `--by`, the reviewer's name, and the log line records it with its standing — `self` (`--by self`, or anyone who has held this issue's lease, every worker it had across takeovers included, and the workers of any other issue on the same **Branch:**), `coordinator` (`coordinator`, `jarl`, `reeve`, the loop's own name — the directory holding `.jarl/` — and any name a `Coordinators: a, b` line in `goal.md` lists) or `fresh` (anyone else); an approve by a `self` is refused, because a self-approve is not a review (a `changes` by one is recorded, not refused); `done` refuses without a live approve inside the gate's window (see [the window of the done gate](profile.md#the-window-of-the-done-gate)); on an issue that carries code — it records **Branch:** or **Merged:** — that approve must be `fresh` (the fresh-review rule): a coordinator's approve is recorded, noted on stderr as not clearing the issue, and refused by `done`, while an issue with neither field (a ruling, a document) still closes on it; a name declared a coordinator after its approve was logged does not count as fresh; `status` and `report` print who reviewed the done work (`fresh a · coordinator b · self c · unrecorded d`, unrecorded for approves that name no reviewer); the output repeats the issue's acceptance, so the verdict is read against it, and ends with one `next:` line naming the step that follows — after an approve of code the merger's one `merged <id> --sha <sha> --ran "<check>" --saw "<summary>"` call and then `set <id> done` (a worker never sets done), after an approve of an issue with no code `set <id> done` once the worker's Proof rows are recorded, after a coordinator's approve of code the fresh reviewer's approve, after `changes` the `round <id>` that sends it back to a worker raised again; findings need at least three words (not `ok`, `x` or `-`) |
| `round <ids> "<what failed>" [--findings <n>]` | one red round on each issue, with the count of findings it left when given; every third round (or every n-th, where a `Takeover (<kind>): <n>` or bare `Takeover: <n>` line of the goal sets it for the issue's kind) prints a takeover block for a fresh worker, which says to raise it one tier up, put it on a model other than the one the lease names, or change the approach (from the top tier, only the last two), and lists the findings per round. The limit is read from the goal at each round, as the goal reads then, and the rounds are counted from the last takeover (or from the first round), so a changed limit takes effect at the next round, whether `goal --set` or a hand edit changed it: lowered to the count or below, the next round takes over; raised, the takeover waits for the count to reach it. Each round's log line carries its standing after its number (`count <k> of <limit>`, or `takeover <k> of <limit>` on the round that takes over), and the count starts again after a takeover; a round line without a standing counts at the fixed limit of three, a takeover at every third such round |
| `tick <id> <line> --by owner` | the owner's tick of an acceptance line only he ticks, the line named by its number among the issue's acceptance lines (see [The owner's sign-off](profile.md#the-owners-sign-off)): refused for any name but the owner's, for a line not marked as his, for a line already ticked and while its material is not there; it writes one log line, `<id> tick · line <n> · by owner · <the line>`, and `show` prints each owner line with its tick under the header. `--json`: `{ id, line, by, at, text }` |
| `models [--by repo\|tag] [--with <root>]... [--archives]` | read-only, no lock: per model, as worker and as reviewer, per kind of issue (`Kind · Tier`), what the record holds — units, clean first passes, changes, rounds, red after approve, handed over, evidence rows before review, follow-ups; verdicts, approves checked by a later reviewer of another model, misses, relayed verdicts, clearing approves on the worker's own or a lower-ranked model — every count with its n and a share only from n ≥ 5, then the words `fits` and `below` (the model's clean share against its kind's baseline), `new` (n < 5 in every kind) and `may clear <kind>` (see [Which model sits where](models.md#which-model-sits-where)); work whose lease or verdict carries no model is grouped `(not recorded) · tier <t>`; ids that are the same once every `.` is written as `-` make one row, which names the spellings it folded; `--by` slices by repository or tag; `--with <root>` (repeatable) reads another loop, a root or an archive directory under `.jarl/archive/`, and `--archives` this loop's own archives, each merged into one table that groups by the model value as recorded and names the loops it read, so a model is calibrated over several loops (thresholds of n ≥ 5 are reached across loops long before they are reached in one); a path that is not a loop is refused and nothing is written; suggestions only |
| `merged <ids> --sha <sha> [--ran "<check>" --saw "<summary>" \| --red <id>] [--ci pending\|green\|red\|none] [--repo <name\|path>] [--keep]` · `merged <ids> --ci <state>` | the merge as fields, not prose: **Merged:** the sha (and where, with `--repo`), **CI:** only when given (`pending`: a pushed commit whose CI will report; `none`: the repository has no CI to wait for), and a log line per issue. `--ran` and `--saw` (paired like `evidence`'s) record the check that decided the merge in the same call, in the merge record of every issue (the **Merge check:** field and the merge line); they write no evidence row, because the merger's check is not the worker's proof (see [Proof, Notes and the merge record](profile.md#proof-notes-and-the-merge-record)), and the reply says so for each issue that holds no Proof row. `--red <id>` records instead a merge that landed while its check was red for a cause outside the branch, which issue `<id>` (it must exist, and is not one of the merged) tracks; it is never counted as a passing check, and the merger uses it only on the jarl's ruling. After it records a sha, it removes each merged issue's worktree and its local branch when that is safe (see the merger's steps) and names what it removed or why it kept it; `--keep` skips that. `--ci` alone moves the CI state of issues that already record a merge; a sha the repository does not know is noted, never refused. `status` counts `merged, CI pending`, `report` prints the sha per done issue |

## The command line

A flag a command does not take is refused with the list of the ones it does, never ignored. A value flag takes the next argument whatever it starts with, so `--ran "--help"` or `--saw "--- FAIL"` records the row; `--flag=value` works too. A note or a title that itself starts with `--` goes after a bare `--` (`evidence 12 -- "--json drops a key"`), and every flag, `--root` included, goes before that `--`: arguments beyond what a command reads are refused, so a stray `--root` can never be dropped silently.

`--version`, given alone as the first argument, prints the version of this install: the version in the manifest of the plugin the skill belongs to, or a fallback version when the copy has no manifest. `resume` prints one line after its counts when the host exports `CLAUDE_PLUGIN_ROOT` and the manifest at that plugin root names another version than this script. The note needs the host to export that variable; a host that does not export it gets no such line. Neither the note nor a missing manifest refuses a call.

### Lists

A list field holds items, and every list field of every command and tool reads them by one rule. The list fields: the `<ids>` of the commands above and the `id` of `answer` (several ratify items), `new`'s `--tags`, `--files`, `--repo`, `--source` and `--after`, `import`'s `--tags`, `--repo` and `--only`, `decide`'s `--settles`, and the last argument of `files` (paths), `source` (references), `after` (the ids waited on) and `repo` (repositories).

- **What a list is.** One item, or several as one comma list (`a,b`; spaces around the commas are dropped, ids take ranges as `<ids>` says). A list flag also repeats (`--tags a --tags b`), and `files`, `source`, `after` and `repo` also take their items as separate words (`files 3 a.mjs b.mjs`). A tool field takes the same text or a list of strings, one item each (`["a", "b"]` as a list, not as text). An item never holds a comma, because the record writes a list as a comma list. Empty items are dropped, so `files <id> ""` clears Files.
- **An item that starts with `-`** is refused: it is a flag in the wrong place, and after a bare `--` it is where a `--root` written last lands. The refusal says that flags go before the `--`.
- **A list written as text** is refused, so brackets and quotes never become part of an item: an item that begins or ends with a quote mark (`"a"`, `'a'`); a name (an issue or question id, a tag, a reference, a finding id) that holds a bracket or a quote mark anywhere (`[drift]`, `["drift"`); a path (an item of Files or Repo) whose brackets do not pair up, which is what a comma inside `[a, b]` leaves, or that is a quoted or empty list in brackets (`["a.mjs"]`, `[]`).
- **A path whose brackets pair up is a name**, because nothing tells it apart from one: `[1]`, `src/[id]/page.tsx`, `[...slug]`, `app/[[...slug]]/page.tsx`.
- `tag` reads a comma list in each operation, one tag for each name: `+a,b` adds `a` and `b`, and `-a,b` takes both off. A `+name` follows the rule of a name. A `-name` matches the tag as it is stored, brackets and quotes included.

On the tools, the `ids` and `id` fields are declared as one string or a list of strings. They come before other arguments, which the adapter types as one string alone, so the tools add the list declaration themselves; a list is joined into the one comma list the command reads. Every other list field is typed as a list of strings, and takes one string as well.

Every command takes `--json` and `--help`. A subagent does not always inherit `CLAUDE_PLUGIN_ROOT`, so
a worker's brief carries the absolute path to the script as well as the tools. Run from a worktree of the repository whose main checkout holds the loop, the script finds the
loop there by itself (default mode: the worktree has none of its own); `--root` still wins when given, and every brief carries the absolute path of
the directory that holds `.jarl/` for it anyway, because a loop that lives in another repository (a hub directing code elsewhere) is not found from the code's worktree,
and in committed mode a worktree holds only the copy it was cut with.

## What is on whom

Every open thing of a loop has one holder who moves next: the owner, the jarl, a coordinator or a person by name. Jarl derives the holder from the record, from the status flags of the loop's profile, the verdicts, the questions and the rulings, never from the name of a status, and stores nothing. `next --as <who>` lists what is on that holder, `status --as <who>` and `resume --as <who>` end with the same list. The order is a display, not a schedule: the owner's lines first, then by how many issues each holds up, a question before an item to ratify, then by priority.

| Open thing | Holder | The command that moves it |
|---|---|---|
| an issue ready to start | the jarl | `set <id> <the lease status> --branch <b> --worker <name>` |
| a lease with no proof yet, or sent back by a round | the jarl, with its worker as the one who does it | `evidence <id> --ran … --saw …` |
| a proof with no verdict, or an approve by a coordinator alone on an issue that carries code | the jarl | `review <id> approve\|changes --by <reviewer> …` |
| the proofs of code with no verdict, all in one line | the jarl, until an open question that begins `start a fresh session to review issues <n>, <m>` (`issue <n>` for one) names them; then the owner | `review <id> approve\|changes --by <reviewer> …`, or `ask "start a fresh session to review issues <n>, <m>"` where no agent can be raised |
| changes asked | the jarl | `round <id> "<what failed>"` |
| an approve not merged | the jarl | `merged <id> --sha <sha> …` |
| merged, or approved with no code, and no owner line waits for his tick | the jarl | `set <id> <the closing status> "<why>"`, or `merged <id> --ci green\|red` while CI is pending |
| an acceptance line only the owner ticks, its material not there yet (no proof after the work was started or last sent back, or a path not found) | the jarl, with its worker as the one who produces it | `evidence <id> --ran … --saw …` |
| an acceptance line only the owner ticks, its material there | the owner, with the material and what to check | `tick <id> <line> --by owner` |
| a question, an item to ratify | the owner | `answer a-<n> …` |
| a ruling in force that settles issues none of which is live (open, in progress or done), and none finished on it | the jarl | `new`, then `decide … --supersedes <slug> --settles <id>` |

With no slice in the loop, a coordinator's lines are the jarl's. An issue waiting on **After:** is on nobody: `--all` shows it on the holder of the issue it waits through, as `waits on X via N`, once for each holder that issue's lines are on. Under a done gate with no approve, a proof is followed by the merge or the close. Under an external scheduler the issues in play are left out and the composer's command is named for them.

## Views for dashboards

Jarl ships no UI. A dashboard, a release board or a weekly summary is rendered by the host (a page, an artifact, a script) from the JSON the tool already prints, so every number on it comes from the record. Every command takes `--json` (the `json` field of its tool). The shapes below are stable: keys are added over time and never renamed or removed without a note in the changelog.

- **`status --json`**: `open`, `in-progress`, `done`, `dropped`, `deferred` (counts per status); `ready` (open, not waiting; null under a profile's `external-scheduler`, which adds `scheduler`), `inFlight` (in progress, not waiting), `waiting` and `waitingIds` (After not settled); `noAcceptance` (in-progress ids with no acceptance line); `questions` (open asks that are not ratify), `ratify` and `toRatify` (`[{ id, state, kind, target, issue, question }]`); `goal`, `opened`, `lastActivity` (log stamps, `YYYY-MM-DD HH:MM` UTC), `archived` (how many archived loops); `stale` (`[{ id, problems: [text] }]`); `ciPending`, `ciRed` (ids); `reviews` (`{ fresh, coordinator, self, unrecorded }`, plus `retracted` when a closed issue's approve was retracted and none stands); `closedGate` (`[{ id, reason, repair }]`, the closed issues whose done gate does not hold, empty when all hold; it follows `inFlightRows` and precedes `uncommitted` in the output); `uncommitted` (count, or null outside the committed modes). With `--by repo|tag|kind|prio`, also `by: { key, groups: { <name>: { open, in-progress, done, dropped, deferred } } }` — an issue naming two repositories, or carrying two tags, counts in each group; an untagged one under `(none)`. `inFlightRows` (`[{ id, title, branch, worker, since, mark, next }]`, one per issue in flight; `mark` is `no-rows`, `rows-no-verdict`, `changes-requested`, `approved`, `approved-not-fresh`, `merged-ci` or `merged`, and `next` says what comes next in words), placed before `uncommitted`; with `--tag`, `tag` comes just before the last key. Last, `check` (`{ declared, checks, landsOn, merges, byRepo }`: the `Check` lines of `goal.md` and what the loop's merges say of its checks, see [Loop metrics](#loop-metrics)). `set <id> ready` (or `review`) is refused naming this view, because those are views and not statuses; a loop that wants an explicit review status declares one in its profile. With `--as <who>`, `as` (the `next --as <who> --json` object) comes after `check`.
- **`report --json`**: `done`, `dropped`, `deferred`, `left`, `found` (counts); `reviews` (as above); `byRepo` (`{ <repo>: [done ids] }`); `text` (the report as printed); `issues`, one row per issue: `{ id, title, status, kind, priority, tier, tags, repos, branch, after, sources, merged, ci, review }`, where `repos` are the repository names it counts under, `merged` the recorded sha or null, `ci` its state or null, and `review` the last approve as `{ by, kind, at }` (`kind` is the reviewer's standing; by and kind are null for an approve that names no reviewer) or null; `check` (as in `status`); `closedGate` (as in `status`); `metrics` (see [Loop metrics](#loop-metrics)).

- **`resume --json`**: `goal`, `opened`, `lastActivity`, `archived`; `status` (the whole `status --json` object); `rulings` (`[{ date, slug, by, line }]`, in force only, `line` the ruling's first line; an answered question's ruling also carries `answer`, the line of its answer, which resume lists before `line`); `inFlight` (`[{ id, title, branch, worker, since, stale, mark }]`, and `next` where an acceptance line only the owner ticks waits before done; `mark` as in `status --json`; in progress and not waiting — as many as `status.inFlight`); `waiting` (`[{ id, title, status, after }]`, open or in-progress issues whose After is not settled — as many as `status.waiting`; an in-progress row also carries `branch`, `worker`, `since`, `stale`); `held` (`[{ id, title, priority, files, heldBy }]`, open issues a taken file holds back, and, with `questions` instead of a holder, those an open question names; `held` and `readyTotal` together are `status.ready`); `questions` and `ratify` (open asks, as in `status`); `next` (`[{ id, title, priority, noAcceptance? }]`, the first `--ready n`) and `readyTotal` (under a profile's `external-scheduler`: `next` and `held` empty, `readyTotal` null, and `scheduler` added); `queue` (the `queue --json` object); `merged` (`[{ id, title, sha, repo, ci }]`, CI pending or red); `tips` (the `tips --json` object); `uncommitted` (paths, or null outside the committed modes); `log` (the last `--log n` lines, without the leading `- `; null with `--log 0`); last, with `--as <who>`, `as` (the `next --as <who> --json` object).

## Loop metrics

`report` ends with the loop's metrics, and `report --json` carries them under `metrics`. They are read from the record alone — the journal and the issue files, never git or a network — so they are as good as the record: a number the record cannot back says **no data**, with the reason in `noData` and null values, never a zero. An approve that names no reviewer has no standing, a loop with no merge has no CI after one. Every metric carries `n`, the issues it was read from; a closed issue is one in a status that closes the record (`done`).

- `check`: `{ declared, checks, landsOn, merges, byRepo }`. Where the repository has a check, the check decides what lands; a fresh reviewer can only stop a change, and its word is recorded as testimony. `goal.md` names the commands: a `Check: <command>` line for the whole loop, a `Check (<repo>): <command>` line for one repository, `<repo>` being the name its Files prefix writes (`declared` and `checks` list them). A repository's declared check is its own `Check (<repo>)` lines, else the loop's `Check:` lines. A merge carries the declared check when the `--ran` text of its merge line equals a declared command after trimming whitespace; a row with any other text, a merge with no row and a repository that declares nothing carry none. `landsOn` is `check` when every merge carries the declared check, `testimony` when none does, `partial` between, and `status` and `report` print the testimony mark for `testimony` and, per repository, `k of n merges carry the declared check`. `merges` is `{ merges, withCheck, noCheck, red }` over the merged issues, counted by each issue's last merge line: `withCheck` carries the declared check, `noCheck` does not (no row, or another command), `red` is `[{ id, cause }]` for merges landed with `--red`. `byRepo` is `{ <repo>: { repo, merges, withCheck, noCheck, red, declared, landsOn, k, n } }`, `k` the merges carrying the declared check and `n` all its merges, an issue naming two repositories counting in each; `status --by repo` and `report` print it.
- `cycleTime`: the first move into progress to the last close, per closed issue: `{ n, of, medianHours, p90Hours, maxHours }`. `leadTime`: the same from the filing.
- `rounds`: `round` lines and `changes` verdicts on the closed issues: `{ n, rounds, issuesWithRounds, changes, issuesWithChanges }`.
- `reopenings`: moves out of a closing status (done back to open or in progress), on every issue the journal tracks: `{ n, times, issues }`. Deferred or dropped work brought back is not a reopening.
- `freshReviews`: the standing of the live approve that cleared each closed issue — `{ n, recorded, fresh, coordinator, self, unrecorded, share }`, `share` fresh among those with a recorded standing; `code`, the same for the closed issues that carry code; `reviewers`, how many each fresh reviewer cleared.
- `redCiAfterMerge`: the merged issues whose CI was recorded red at any point after the merge, among those whose CI settled green or red: `{ n, settled, red, issues, share, pending, none }`.
- `followUps`: an issue filed within 7 days after a closed issue first closed, whose **Found by** names that issue's number (a reviewer's name such as `reviewer-450` counts; a number inside a sha does not): `{ windowDays, n, windowOpen, withFollowUps, windowClosed, windowClosedWithFollowUps, share, followUps: [{ id, followUps }] }`. A closed research issue is left out: the issues filed from it are its product. `windowOpen` counts the closes whose 7 days have not passed yet; `share` is taken over the `windowClosed` ones only, because a close whose window is still open has not yet shown it has no follow-up (null while none has passed).
