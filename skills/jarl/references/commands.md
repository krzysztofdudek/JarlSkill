# The commands

Every command of the tool with its flags, the fields the MCP tools take, the grammar of the command line, the JSON each view prints, and the loop metrics. The exact options of any command are printed by the tool itself: run `jarl.mjs --help`, or call the `jarl_help` tool, and read that text where this file and the help differ. Read this file when a command's behaviour is in question, or to see what a view carries. The terms are defined in [glossary.md](glossary.md).

## The tools and their fields

The fields, command by command:

- the flags `--acceptance`, `--changelog`, `--outside`, `--ran` and `--saw` repeat, so their fields are lists, and `ran` and `saw` pair up by position; the list flags (`new`'s `--tags`, `--files`, `--repo`, `--source` and `--after`, `import`'s `--tags`, `--repo` and `--only`, `evidence`'s `--line`, `decide`'s `--settles`) repeat too, and their fields are lists of items. The flag fields: `init` committed, permanent, profile, by · `renumber` key, by · `new` kind, prio, tier, tags, files, repo, found-by, where, what, why, acceptance, source, after, changelog, template, field, section, person, check-when, range, by · `import` source, kind, prio, tier, tags, repo, found-by, only, adopt, dry-run, field, parent, by · `sources` source · `evidence` ran, saw, line, file, slot, by · `retract` by · `field` add, remove, clear, by · `split` line, by · `base` by · `list` status, kind, tag, prio, grep, match, all · `show` full · `brief` role, slice · `set` branch, worker, model, worktree, handover, header, without-rows, by · `next` limit, all, as, slice · `review` by, model, relayed, bot, outside, field, artifact · `round` findings, by · `tick` by · `models` group, with, archives · `scope` branch, base, repo · `branches` base, repo, stale-hours · `merged` sha, ci, repo, ran, saw, red, keep, by · `ask` kind, target, issue, slice, option, applies-to, until, to, by · `answer` by, option · `resume` log, ready, gh, repo, base, as, slice · `log` by · `decide` settles, waives-review, by, quote, under, supersedes, applies-to, until, area, reach, rule · `decisions` live · `goal` set, by · `status` stale-hours, group, tag, as, slice · `archive` by · `report` found, metrics · `mode` by · `changelog` repo · `close` force, batch, by · `extend` values, default, required, by;
- the argument fields, in the order the usage writes them: `init` goal · `new` title · `renumber` id · `import` file · `sources` files · `evidence` ids, text · `retract` id, entry, text · `field` ids, name, value · `split` id · `base` name, branch · `show` id · `brief` id · `set` ids, status, text · `merged` ids · `review` ids, verdict, text · `round` id, text · `tick` id, line · `scope` id · `ask` text · `answer` id, text · `log` text · `decide` slug, text · `archive` slug · `changelog` ids · `mode` mode · `profile` file · `extend` part, name · `use` path (`sources` takes a list in its last field, the findings files, and `field`'s `value` a comma list for a list field; the `id` of `round` takes one id or a list with ranges, and the call lands on every id or on none; every list field reads its items by the one rule in [Lists](#lists)); the absolute paths are `import`'s `file`, `sources`' `files`, `init`'s `profile` and `profile`'s `file`;
- every tool takes `json` (true answers with what `--json` prints) and `root` (what `--root` is: the checkout that holds `.jarl/`, as an absolute path — a relative or empty one is refused).

The answer is the text the command prints; a note the command prints on stderr comes as a second block. A refusal is an error result with its reason, and nothing was written; a `scope` that found something wrong is an error result too, with its items (the CLI's exit code 2). Jarl has no error document: with `json: true` a refusal's one block is the reason as plain text. A value that starts with `--` is just a value in a field, except an item of a list, which [Lists](#lists) refuses. When a call gave no `root`, the answer names the loop it reached: as a block after the text, or, with `json: true`, in `_meta['jarl/loop']` instead, and the CLI's stderr notes go into `_meta['jarl/warn']` the same way, so a host that parses the one JSON block never has to skip anything.

**Which loop a call reaches:** its `root` field; without it, the loop the session named with `use <path>`, which the server holds for that session alone, in its own process, never in the record or a file, until `use` names another (the command line keeps nothing between runs, so there `use` prints the `JARL_ROOT` setting to export for each shell, and the command line reads `JARL_ROOT` after `--root`); without that, the server's `JARL_ROOT` environment variable (set it in the server's configuration to pin one loop — as an absolute path: a relative one is refused, for the same reason a relative `root` is, rather than resolved against the server's own working directory); without that, the loop found from the directory the host started the server in — the session's project — the way the CLI finds it from its own working directory: at the root of that checkout, or of its main checkout from a worktree that holds no loop of its own, and never in a subdirectory (a loop kept in one is reached only through `root`, `--root`, `JARL_ROOT` or `use`). Discovery lists the loops under that checkout by a walk at most four directories down that enters no hidden directory, no `node_modules` or `vendor` and no other checkout (a directory with a `.git` of its own: a worktree, a submodule), follows no link and stops after 5000 directories; `use` with no path prints that list. Where the root holds a loop it is the one reached, and a note names the others; where it holds none and loops are below, a call that names none is refused with the list, `init`, `use` and `profile` with a file excepted, which read the checkout or the file itself. The server lives as long as the session, not in the worktree a role works in, so every brief says to pass `root` on every call (see [The command line](#the-command-line) for the same rule on the command line).

## The commands

| Command | What it does |
|---|---|
| `init "<goal>" [--committed] [--permanent] [--profile <profile.json>] [--by who]` | creates `.jarl/` with the goal and a `.gitignore` that keeps the loop out of git; `--profile` checks the profile file against the schema and stores it as `.jarl/profile.json` (see [Profiles](profile.md#profiles)); `--committed` writes a `.gitignore` that ignores only the write lock and temporary files, so the loop is committed with the work; `--permanent` is committed the same way, adds `.jarl/.permanent`, and opens the loop with no feature branch of its own — see [Where the loop lives](record.md#where-the-loop-lives); on the command line it says once when the goal names no `Check` line: the loop then lands on testimony alone, whatever its merges record, until the goal declares one; and once when the goal declares no `Model` line: no model is placed and `models` ranks none until it does, with the `goal --set` form that adds one |
| `new "<title>" [--kind k] [--prio 1\|2\|3] [--tier light\|standard\|strong] [--tags a,b] [--files p,q] [--repo <name-or-path>] [--found-by who] [--where w] [--what w] [--why w] [--acceptance line]... [--changelog entry]... [--source <report-dir#finding-id>] [--after <ids>] [--template <name>] [--field "<name=value>"]... [--section "<name=value>"]... [--person "<name>" --check-when "<date-or-event>"] [--range <name>] [--by who]` | files an issue under the next free number; `--range <name>` files it under the next free number of a range the goal declares (`Range (<name>): <from-to>`), and every other filing takes its number outside every declared range, so one series never moves the count of another; the first number from a range raises the loop to record format 3, and is refused with nothing written in a loop a composer keeps; `--kind promise` files a promise, kept by whoever `--found-by` names (the jarl when none), and `--kind wait` a wait on an outside person, which needs `--person` (who it is held by) and `--check-when` (a date, or the event to check after), refused without them and on any other kind; filing either raises the loop to record format 3, and is refused with nothing written in a loop a composer keeps (see [What is on whom](#what-is-on-whom)); `--field` and `--section` (repeat each) write a field and a section the loop's profile declares, a field's default when it is not given and a required one refused when it is missing (see [Profiles](profile.md#profiles)); without `--tier` it records `standard` and says so on stderr, with what each tier is for (see [Which model sits where](models.md#which-model-sits-where)); `--repo` names the repository its code lives in when that is not the loop's own (see [Code in another repository](repositories.md#code-in-another-repository)); `--where`, `--what`, `--why` and `--acceptance` (repeat it, one checkable line each) write the body in the same call, `--changelog` its changelog entry (see [Changelog fragments](worker.md#changelog-fragments)), `--source` names the research finding it comes from, `--after` the issues it waits on; `--template` starts from `.jarl/templates/<name>.md` (see [Templates](jarl.md#templates)); the reply's first line is `filed 7 · file`, then it lists what was parsed (priority, tier, kind, tags, acceptance lines, the length of What and Why) and every field left empty with the command that fills it; a What, Why or section text that holds a matched `<why>…</why>` pair (the name of any field) outside code is refused, because the fields belong in their own parameters; from a linked worktree of a committed loop whose main checkout holds the same loop, `new` refuses and names the main checkout as the root to pass, and from anywhere else the number is the highest over the main checkout, every linked worktree and every local and remote-tracking branch of the repository, plus one; the issue gets a key, written in its header and on every log line about it, which raises the loop to record format 3, and none in a loop a composer keeps (see [The log is the record](record.md#the-log-is-the-record)) |
| `renumber <id> --key <key> [--by who]` | of the issue files that carry one number after a merge of two copies of the loop, gives the one whose header carries `--key` the next free number, as `new` takes one: renames its file and rewrites its first line; every log line about it names its key, so it keeps them under its new number, no line is rewritten, and one line `<new> renumbered from <old> · issues/<file>` is added; refused for a number one file carries, without `--key` (naming the files and their keys) and for a key no file of the number carries |
| `field <ids> <name> ["<value>"] [--add \| --remove \| --clear] [--by who]` | the one command that changes the description of a filed issue (see [The description and the history](record.md#the-description-and-the-history)), on every id: a header field — **Title** (the heading only; the file keeps its name), **Priority:**, **Tier:**, **Kind:** (the last three against their values, the profile's for Tier and Kind), **Found by:**, **Tags:**, **Files:**, **Repo:**, **After:**, **Source:**, **Where:**, **Resources:** (the exclusive resources an issue holds while its lease lasts, see [The issue file](record.md#the-issue-file)), **Parent:** (the one issue it is a sub-issue of, see [Filing an issue](jarl.md#filing-an-issue)), **Person:** and **Check when:** (whom a wait is held by and when to check it, written on any issue so that Kind can become `wait` once both are there, never emptied on a wait), a field the loop's profile declares — or a section: What, Why, Acceptance, Changelog and a section the profile declares. A name is matched in any case; one with a space is quoted (`"Found by"`). A value alone replaces what the part holds; `--add` adds the items of a list field (Tags, Files, Repo, After, Source, Resources), each issue keeping what it held, or the value after what a section holds (Acceptance and Changelog gain lines, one per line of the value; the others a paragraph); `--remove` takes items off a list field (an item an issue does not hold is not there to take, and a list emptied so is cleared); `--clear` empties an optional part, and Title, Priority, Tier, Kind, Found by and a field the profile requires are never empty. A list field takes a comma list; **After:** names the issues it waits on (`next` does not offer it until each is done or dropped, `status` counts it as waiting, and a chain that would come back to the issue is refused); **Repo:** may name several repositories, by name or by path (see [Code in another repository](repositories.md#code-in-another-repository)); a `slice:<coordinator>` tag puts an issue in that coordinator's slice, and a second `slice:` tag on one issue is refused with the calls that move it, the same slice in another case too (slice names compare in any case, and `--remove slice:<name>` takes it off in any case). Each change writes a log line per issue and part that records what it held before and, when `--by` names someone, who changed it, and a value the part already holds writes none; a change that adds or rewrites an acceptance line of a leased issue notes each such line on stderr (its scope grew after the lease) and its log line carries `· grew after the lease: line <n>`; any other name is refused with the names `field` writes and the command that writes that one (`set` for the status and the lease, `merged` for a merge and its CI, none for the history) |
| `split <id> --line "<line=id>"... [--by who]` | shares out the acceptance lines of a parent among its sub-issues in one write: each `--line <n>=<id>` moves line n to issue `<id>`, or keeps it on the parent when `<id>` is the parent's own; every line is named once and a line named nowhere is refused, so none is lost; each issue a line moves to becomes a sub-issue, as `field <ids> Parent <id>` makes one and with its refusals, and gains the line after the ones it holds (see [Filing an issue](jarl.md#filing-an-issue)); a leased sub-issue that gains a line is noted and marked as `field` notes and marks it, and a row of the parent that names a line the split moved or renumbered is noted as `field` notes it (a row keeps the number it named) |
| `base <name> <branch> [--by who]` | changes the base branch a declared repository is held against, with a log line that says what it was (see [Code in another repository](repositories.md#code-in-another-repository)) |
| `import <findings.json> [--source <report-dir>] [--kind k] [--prio p] [--tier t] [--tags a,b] [--repo <name-or-path>] [--found-by who] [--only <ids>] [--adopt] [--dry-run] [--field "<name=value>"]... [--parent <id>] [--by who]` · `sources [<findings.json>...] [--source <report-dir>]` | research findings into issues, once each, and the coverage view — see [From research to issues](jarl.md#from-research-to-issues) |
| `list [--status s] [--kind k] [--tag t] [--prio p] [--grep re] [--match "<field=value>"]... [--all]` | open and in-progress by default, sorted by priority; `--all` lists every status; `--match` keeps the issues whose header field holds the value (any field, a profile's own included; repeat it to require several); a sub-issue stands indented under its parent, and one whose parent is not listed names it |
| `show <id> [--full]` · `status [--stale-hours n] [--group repo\|tag\|kind\|prio\|<name>] [--tag <tag>] [--as <who>] [--slice <coordinator>]` | one issue as the done gate sees it — the header, What, Why, Acceptance and Changelog; every `--ran`/`--saw` row (numbered `[n]` over the whole Evidence section, the number `retract` takes) and every verdict in [the gate's window](profile.md#the-window-of-the-done-gate); every `changes` finding no later approve has answered; one line for each round that came before; last, the exact call that prints everything — `--full` prints the file (rows still numbered), `--json` is complete; under the header, where each repository written as a name is on this machine and the worktree git has on the lease's branch (`--json`: `where`), on stdout only · the loop's goal, when it was opened and when anything last happened, then one line of counts (open, in flight, waiting, done, dropped, deferred, questions, to ratify, merged with CI pending or red), then the landing banner — one line per repository, `k of n merges carry the declared check`, or the testimony mark for a repository that declares no check and while no merge carries the declared check — and, with `--group repo`, the merges of each repository by what they carry (the declared check, not, landed on red), then, once an issue carries a `slice:` tag, one line naming each coordinator with its slice and how many of its issues are in play, and a slice whose coordinator the `Coordinators:` line does not name (`--json`: `slices`, each `{ coordinator, tag, declared, inPlay }`), then the choices awaiting ratification, the stale leases, the merges waiting on CI, the waiting issues, the parents waiting on their sub-issues and those whose sub-issues are all closed (`waitingOnSubs` and `parents` in `--json`), the issues in flight with no acceptance line, one line for each issue in flight that says what the record shows and what comes next (`no evidence rows since the start`; `evidence rows recorded, no verdict` — it waits for a reviewer; `changes requested` — back with the worker; `approved and queued` — the merger lands it, then it is set done; `approved by a coordinator only` on an issue that carries code — the merge queue and done refuse that, it waits for a fresh reviewer; `merged, CI not green yet` — record the CI result; `merged` — set it done; derived from the evidence rows and verdicts after the last start or round, never stored, so no status carries it) and, in a committed or permanent loop, how many loop files git has not committed; `--group` adds the five status counts per repository, tag, kind, priority or a field the profile declares (see [Views for dashboards](#views-for-dashboards)); `--tag <tag>` computes every part of `status` (the counts, in flight, stale, waiting, CI, the questions that name those issues, the reviews) over the issues carrying that tag only, for a jarl directing one scope of a large loop — the tag is refused when no issue carries it, `--json` has the same shape plus `tag`; `--slice <coordinator>` does the same over the issues tagged `slice:<coordinator>`, with the escalations that name the slice (`slice` in `--json`), refused when the goal's `Coordinators:` line names no such coordinator and no issue carries the tag, and the goal, the loop files not committed and the check state stay the loop's own; all three print one `record:` line for each header field that disagrees with the log (`disagreements` in their `--json`, only when there are any), see [When a header disagrees with the log](record.md#when-a-header-disagrees-with-the-log); `status --as <who>` ends with what `next --as <who>` prints (`as` in `--json`) |
| `brief <id> [--role worker\|reviewer]` · `brief --slice <coordinator>` | read-only, the brief a role is raised with, assembled from the record when asked: for an issue's worker (the default) or reviewer, the issue as `show` prints it, without the lines that name where a repository or a worktree is on this machine, a `Worktree:` field of the header among them; the rules with a scope that reach that reader (its role, its moment: the start or the review, and the round once a round sent the work back; the issue's tags, kind, tier, files, repository and slice) and Jarl's own, whole (see [Rules with a scope](jarl.md#rules-with-a-scope)); the rounds so far; the findings of every review that sent it back, each once in the log's order: whole where the issue's Reviews section holds that verdict's entry, else as the log's line holds them, its lead-in included, which for a text of several lines is its first line and a count of the lines left out; an entry is a verdict's when every pairing of the log's review lines, approves and retractions among them, with the section's entries that pairs the most pairs the two, each pair agreeing on everything both record (the verdict, the reviewer and its standing as written then, the model, the relay mark, the batch, the text the line holds, read with or without the `findings: ` lead-in a writer sets before a finding that opens like a mark, and the day where both have one) and each pairing keeping the order of both, or any order, with a note that says so, where no pairing in that order places every entry a line fits; an entry the pairings disagree on, which another line or entry of the same reviewer fits as well, goes to no verdict: each gives its log line, and the entry is listed after them, marked as the issue file's alone, with a note, as is an entry that matches no verdict line; the proof rows; the role's reference; and the commands that record the result, each with a placeholder for every value. A worker on an issue taken over, a lease handed to a new worker with a reason that names the takeover, is given the rules of the takeover too; a round that printed the takeover block is not one until that handover is recorded. `--slice` is the coordinator's: its issues in play, its rules, its reference, `next --as <coordinator>` and its escalation; a slice the `Coordinators:` line does not name is briefed with a note that says so. | `set <ids> <status> "<text>" [--branch <worker-branch>] [--worker <name>] [--model <model-id>] [--worktree <path>] [--handover] [--header] [--by who]` | changes status and writes the log line in one move; a lease that finds the lines closes the offer, and a lease after they are gone offers it again; no view holds it) |
| `evidence <ids> "<text>" [--by who]` \| `evidence <ids> --ran "<command>" --saw "<what-it-printed>" [--line <line-number>]` \| `evidence <id> --file <path> --slot <name> [--line <line-number>]` | appends a free-text note, or one checkable row per `--ran`/`--saw` pair (repeat the pair for more rows, in one call or several) — `--ran`/`--saw` for what proves the work, free text for what only explains it (rows go to Proof and text to Notes, see [Proof, Notes and the merge record](profile.md#proof-notes-and-the-merge-record)); `--file`/`--slot` records one file as an attachment, a Proof row of its own (see [Attachments](profile.md#attachments)); nothing already recorded is ever replaced; a free-text note that runs long is written whole and noted on stderr (command line only). `--line <line-number>` (repeated, or a comma list) names the acceptance lines every row of the call proves, `1` for the first as `tick` counts them: the row is written `- **ran (line 1, 3):** …` and its log line `<id> evidence row (line 1, 3) · …`, and `show`, `brief` and the record library read the numbers back. A number the issue has no acceptance line for, a number that is no whole number, `--line` on a note and `--line` on an issue with no acceptance line are refused, with nothing written. The first row that names a line raises the loop to record format 3 (a loop a composer keeps below it refuses the row). From that row on, whichever issue it was recorded on, the whole loop names lines, and `done` asks of every issue it closes a counted row (inside the gate's window, not retracted) that names each acceptance line, a line only the owner ticks excepted, for his tick proves it: a row without `--line` proves no particular line. `done` lists the lines no such row names and refuses, ending with the form of `set <id> done "<text>" --without-rows "<why-no-row-names-the-lines>"`: the reason for those lines is given apart, because `"<text>"` is the move's reason and never stands for it. With `--without-rows` it closes, writes `Done without a row naming acceptance line 2, 3: <why>` under Evidence, says so on stderr, and `report` marks the issue so; `--without-rows` on a call that leaves no such line, or in a loop that names none, is refused. An approve says the same lines in its note, with the same form. A closed issue is read against the rule again: a line a counted row named at the close and none names now (its row retracted) is flagged by `status` and `report` until a row names it again; a line added to the acceptance after the close is read as one the close left without a row, and `report` marks it so. A row keeps the numbers it named when the acceptance is rewritten after it, and `field` notes it where rows name any. The test that runs `verify` on real loops is skipped unless `JARL_LIVE_LOOP` names copies of them (each the directory that holds the copy's `.jarl`, several separated by the platform's path separator); `JARL_LIVE_KNOWN=1` also checks the two findings a frozen copy of the release loop is known to hold, a struck-through verdict line and an open issue citing a superseded ruling |
| `mode permanent [--by who]` | turns an existing, committed loop into the permanent mode, with a log line — for a loop opened `--committed`; refuses a default-mode loop (out of git — a permanent record must be committed) and an already-permanent loop |
| `profile [<profile.json>]` | read-only: the loop's profile — its statuses and what each one means, the status a new issue starts in, the values of Kind and Tier, its fields and sections and the heading its acceptance lives under; the built-in profile when the loop has none; with a file, that file checked against the profile schema, and the loop is not touched (see [Profiles](profile.md#profiles)) |
| `use [<path>]` | read-only, nothing written: with no path, the loops under the checkout, as discovery finds them (see the tools above); with a path (relative to the checkout, as the list prints it, or absolute) that holds `.jarl/`, the loop the calls that follow reach when they name none — the tool session keeps it, and the command line prints the `JARL_ROOT` setting for a POSIX shell, PowerShell and cmd, each line naming its shell; a path with no loop is refused with the list |
| `extend section "<name>"` · `extend field "<name>" [--values "<items>"] [--default "<value>"] [--required] [--by who]` | adds one section or one field to the profile of a live loop, checked as `profile <profile.json>` checks a file, with a log line `profile extended · <section-or-field>`; a loop with no profile gets one with the built-in statuses, in the record format it is in. Kind and Tier keep the values the loop was opened with. The issues already filed are not rewritten: each carries the part once `field` writes it, and a new issue is filed with it, a field's default when none is given. Refused, with nothing written, in a loop a composer runs (see [Profiles](profile.md#profiles)). After it, a loop that had no profile has one of its own, named `custom`, and reads as a loop with a profile: `status --json` keeps its counts under `statuses` (see [Profiles](profile.md#profiles)). `extend` only adds: a part it added is changed or taken out by editing `.jarl/profile.json` by hand, which every command then checks |
| `close [--force] [--batch] [--by who]` | refuses while anything is open or in progress, and, where it removes `.jarl/`, while anything is deferred, because deferred work waits and removing the directory would leave it waiting nowhere: the refusal names `archive "<slug>"`, which keeps the loop under `.jarl/archive/` with its deferred issues, and `--force`, which closes anyway, with issues still open or in progress (list them to the owner first) and with deferred ones, and removes the loop with them and keeps no copy (the output names the deferred issues as removed); otherwise removes the live loop's files, and `.jarl/` itself when it holds no archive. In the default mode `close` and `init` leave `.jarl/archive/` in place, and `close` says so; in the committed mode the archive is committed content, so `close` refuses while `.jarl/archive/` holds anything, names it, and says to move it out of the tree or pass `--force`, which removes the whole directory and says so (an empty archive directory is fine); in the permanent mode it keeps the directory instead and logs the close; in a committed or permanent loop it names the loop files git has not committed; first it files the ratification batch (see [Rulings about an area](jarl.md#rulings-about-an-area)) and offers each rule of the loop with a scope for promotion (see [Rules with a scope](jarl.md#rules-with-a-scope)), and never waits for either; `--batch` files them and closes nothing (`batch` and `promotion` in `--json`, `promotion` `{ items, filed, off }`) |

`<ids>` on `field`, `round`, `evidence`, `review`, `set`, `merged` and `changelog` is one id or several, written as one comma list with ranges: `12,13,14` or `203-206,209`. The tool resolves every id and checks every precondition before it writes anything, so a package of issues merged together closes in four calls (evidence, review, `merged`, `set done`) instead of four per issue, and one missing id or one issue not ready for `done` leaves all of them untouched. Each issue still gets its own log line.

## The command line

A flag a command does not take is refused with the list of the ones it does, never ignored. A value flag takes the next argument whatever it starts with, so `--ran "--help"` or `--saw "--- FAIL"` records the row; `--flag=value` works too. A note or a title that itself starts with `--` goes after a bare `--` (`evidence 12 -- "--json drops a key"`), and every flag, `--root` included, goes before that `--`: arguments beyond what a command reads are refused, so a stray `--root` can never be dropped silently.

`--version`, given alone as the first argument, prints the version of this install: the version in the manifest of the plugin the skill belongs to, or a fallback version when the copy has no manifest. `resume` prints one line after its counts when the host exports `CLAUDE_PLUGIN_ROOT` and the manifest at that plugin root names another version than this script. The note needs the host to export that variable; a host that does not export it gets no such line. Neither the note nor a missing manifest refuses a call.

### Lists

A list field holds items, and every list field of every command and tool reads them by one rule. The list fields: the `<ids>` of the commands above and the `id` of `answer` (several ratify items), `new`'s `--tags`, `--files`, `--repo`, `--source` and `--after`, `import`'s `--tags`, `--repo` and `--only`, `decide`'s `--settles` and `--waives-review`, and the value `field` gives Tags, Files, Repo, After and Source.

- **What a list is.** One item, or several as one comma list (`a,b`; spaces around the commas are dropped, ids take ranges as `<ids>` says). A list flag also repeats (`--tags a --tags b`). A tool field takes the same text or a list of strings, one item each (`["a", "b"]` as a list, not as text). An item never holds a comma, because the record writes a list as a comma list. Empty items are dropped.
- **An item that starts with `-`** is refused: it is a flag in the wrong place, and after a bare `--` it is where a `--root` written last lands. The refusal says that flags go before the `--`.
- **A list written as text** is refused, so brackets and quotes never become part of an item: an item that begins or ends with a quote mark (`"a"`, `'a'`); a name (an issue or question id, a tag, a reference, a finding id) that holds a bracket or a quote mark anywhere (`[drift]`, `["drift"`); a path (an item of Files or Repo) whose brackets do not pair up, which is what a comma inside `[a, b]` leaves, or that is a quoted or empty list in brackets (`["a.mjs"]`, `[]`).
- **A path whose brackets pair up is a name**, because nothing tells it apart from one: `[1]`, `src/[id]/page.tsx`, `[...slug]`, `app/[[...slug]]/page.tsx`.
- Items `field` takes off with `--remove` match the items as they are stored, brackets and quotes included.

On the tools, the `ids` and `id` fields are declared as one string or a list of strings. They come before other arguments, which the adapter types as one string alone, so the tools add the list declaration themselves; a list is joined into the one comma list the command reads. Every other list field is typed as a list of strings, and takes one string as well.

Every command takes `--json` and `--help`. A subagent does not always inherit `CLAUDE_PLUGIN_ROOT`, so
a worker's brief carries the absolute path to the script as well as the tools. Run from a worktree of the repository whose main checkout holds the loop, the script finds the
loop there by itself (default mode: the worktree has none of its own); `--root` still wins when given, and every brief carries the absolute path of
the directory that holds `.jarl/` for it anyway, because a loop that lives in another repository (a hub directing code elsewhere) is not found from the code's worktree,
and in committed mode a worktree holds only the copy it was cut with.

## What is on whom

Every open thing of a loop has one holder who moves next: the owner, the jarl, a coordinator or a person by name. Jarl derives the holder from the record, from the status flags of the loop's profile, the verdicts, the questions and the rulings, never from the name of a status, and stores nothing. `next --as <who>` lists what is on that holder, `status --as <who>` and `resume --as <who>` end with the same list. The order is a display, not a schedule: the owner's lines first, then a lease or a proof idle past the threshold, then by how many issues each holds up, a question before an item to ratify, then by priority.

| Open thing | Holder | The command that moves it |
|---|---|---|
| an issue ready to start | the coordinator of its slice; with no slice, the jarl | `set <id> <status> --branch <worker-branch> --worker <name> --model <model-id>` |
| a parent whose sub-issues are all done or dropped, and no proof after the last of them closed | the coordinator of its slice; with no slice, the jarl: it checks the parent's own acceptance against the whole | `evidence <id> --ran … --saw …`, then `review` and the close |
| a lease with no proof yet, or sent back by a round | the coordinator of its slice (with no slice, the jarl), with its worker as the one who does it | `evidence <id> --ran … --saw …` |
| a proof with no verdict, an approve by a coordinator alone on an issue that carries code, or approves that do not clear it under the done gate's `"clears"`; several of one kind are one line per holder, cut into the units below | the coordinator of its slice; with no slice, the jarl | `review <id> <verdict> --by <reviewer> …` |
| the proofs of code with no verdict, one line per holder, cut into units one fresh reviewer takes under Jarl's rule for a shared review (one contract or one screen, at most four): the issues of one branch of one repository, leased as one package and read as one diff, at most four to a unit (a branch of more is cut into units as even as they come), each named by its branch (`1, 2, 3 (one branch, jarl/a) · 7`, with its repository where another repository has a branch of that name: `jarl/a in tool`), and every other issue alone (`units` in `--json`) | the coordinator of their slice (with no slice, the jarl), until an open question that begins `start a fresh session to review issues <ids>` (`issue <n>` for one; a plain question only, a ratify item or an escalation holds nothing) names them; then the owner | `review <ids> <verdict> --by <reviewer> …` over one unit, one review with one batch id, or `ask "start a fresh session to review issues <ids>"` where no agent can be raised |
| changes asked | the coordinator of its slice; with no slice, the jarl | `round <id> "<text>"` |
| a lease conflict: an issue the log leases twice, by two writers, with no move out of the lease between the two lines and no handover (two copies of the loop that each leased it before either saw the other, merged) | the jarl | `set <id> <status> --handover --branch <worker-branch> --worker <name> "<why-the-worker-changed>"`, naming the lease to keep: either of the two |
| an approve not merged | the holder the goal's `Merger:` line names, the jarl or one coordinator, for every slice; with no such line, the jarl | `merged <id> --sha <sha> …` |
| merged, or approved with no code, and no owner line waits for his tick | the jarl | `set <id> <status> "<text>"`, or `merged <id> --ci <ci-state>` while CI is pending |
| an acceptance line only the owner ticks, its material not there yet (no proof after the work was started or last sent back, or a path not found) | the jarl, with its worker as the one who produces it | `evidence <id> --ran … --saw …` |
| an acceptance line only the owner ticks, its material there | the owner, with the material and what to check | `tick <id> <line-number> --by <the-owner-himself>` |
| a question, an item to ratify | the owner | `answer a-<n> … --by <the-owner-himself>` |
| an escalation (`ask --kind escalation`) | the jarl | `answer a-<n> "<text>" --by jarl` |
| a ruling in force that settles issues none of which is live (open, in progress or done), and none finished on it | the jarl | `new`, then `decide … --supersedes <slug> --settles <id>` |
| a promise (kind `promise`), open; once given to a worker, the rows of an issue in play | whoever its **Found by:** names, the owner, the jarl, a coordinator or anyone by name | `evidence <id> --ran … --saw …` to record it kept, then `review` and the close |
| a wait (kind `wait`) with nothing recorded yet | the outside person its **Person:** names, with its **Check when:** | `evidence <id> --ran "<command>" --saw "<what-it-printed>"` when it comes |
| a wait whose proof is recorded | the jarl | `review <id> …`, then the close |

A command that is the owner's act, his answer or his tick, is printed with `<the-owner-himself>` for `--by`, and a yes or a reject as `<yes-or-reject-first>`, so a line pasted as printed is refused and writes nothing until the one who holds it fills them in. The coordinator of a slice is the name of its `slice:<coordinator>` tag, written as the goal's `Coordinators:` line writes it; with no slice in the loop, a coordinator's lines are the jarl's, and a coordinator whose slice holds no issue is told so. The rows of a slice reserve files within that slice only: across slices only leases hold. An issue waiting on **After:**, and a parent waiting on its sub-issues, is on nobody: `--all` shows it on the holder of the issue it waits through, as `waits on X via N`. Under a done gate with no approve, a proof is followed by the merge or the close. Under an external scheduler the issues in play are left out and the composer's command is named for them.

## Views for dashboards

Jarl ships no UI. A dashboard, a release board or a weekly summary is rendered by the host (a page, an artifact, a script) from the JSON the tool already prints, so every number on it comes from the record. Every command takes `--json` (the `json` field of its tool). The shapes below are stable: keys are added over time and never renamed or removed without a note in the changelog.

- **`status --json`**: `open`, `in-progress`, `done`, `dropped`, `deferred` (counts per status); `ready` (open, not waiting; null under a profile's `external-scheduler`, which adds `scheduler`), `inFlight` (in progress, not waiting), `waiting` and `waitingIds` (After not settled); `noAcceptance` (in-progress ids with no acceptance line); `questions` (open asks that are not ratify), `ratify` and `toRatify` (`[{ id, state, kind, target, issue, question }]`); `goal`, `opened`, `lastActivity` (log stamps, `YYYY-MM-DD HH:MM` UTC), `archived` (how many archived loops); `stale` (`[{ id, problems: [text] }]`); `liveness` (`{ minutes, from, leases }`: the threshold, `goal`, `default` or `stale-hours`, and per lease its ages and the clones and refs read), right after `stale`; `ciPending`, `ciRed` (ids); `reviews` (`{ fresh, coordinator, self, unrecorded }`, plus `retracted` when a closed issue's approve was retracted and none stands, `relayed` and `bot` for the closed issues a relayed fresh approve or a bot's cleared, and `relayedVerdicts` and `botVerdicts`, every such verdict the record holds, each only when not 0); `closedGate` (`[{ id, reason, repair }]`, the closed issues whose done gate does not hold, empty when all hold; it follows `inFlightRows` and precedes `uncommitted` in the output); `uncommitted` (count, or null outside the committed modes). With `--group repo|tag|kind|prio`, also `by: { key, groups: { <name>: { open, in-progress, done, dropped, deferred } } }` — an issue naming two repositories, or carrying two tags, counts in each group; an untagged one under `(none)`. `inFlightRows` (`[{ id, title, branch, worker, since, mark, next }]`, one per issue in flight; `mark` is `no-rows`, `rows-no-verdict`, `changes-requested`, `approved`, `approved-not-fresh`, `approved-not-cleared` (its approves do not meet the done gate's `"clears"`, or a bot's stands alone), `approved-model-refused` (the profile's `"reviewer"` rule refuses its live approve for its model, as `done` and the merge queue do, and `next` names what is missing), `merged-ci` or `merged` (`approved` while the merge recorded does not count for the code as it is now, as `done` reads it), and `next` says what comes next in words), placed before `uncommitted`; with `--tag`, `tag` comes just before the last key. Last, `check` (`{ declared, checks, landsOn, merges, byRepo }`: the `Check` lines of `goal.md` and what the loop's merges say of its checks, see [Loop metrics](#loop-metrics)). `set <id> ready` (or `review`) is refused naming this view, because those are views and not statuses; a loop that wants an explicit review status declares one in its profile. With `--as <who>`, `as` (the `next --as <who> --json` object) comes after `check`.
- **`report --json`**: `done`, `dropped`, `deferred`, `left`, `found` (counts); `reviews` (as above); `byRepo` (`{ <repo>: [done ids] }`); `text` (the report as printed, the metrics alone under `--metrics`); `issues`, one row per issue: `{ id, title, status, kind, priority, tier, tags, repos, branch, after, sources, merged, ci, review, parent }`, where `repos` are the repository names it counts under, `merged` the recorded sha or null, `parent` the issue it is a sub-issue of or null, as in `list` and `show`, `ci` its state or null, and `review` the last approve as `{ by, kind, at }` (`kind` is the reviewer's standing; by and kind are null for an approve that names no reviewer) or null; `check` (as in `status`); `closedGate` (as in `status`); `metrics` (see [Loop metrics](#loop-metrics)).
- **`resume --json`**, its `queue`: `repos: [{ repo, path, base, rows: [{ branch, issues, waitingReview, waitingModel?, ready, ahead, approvedAt, by, files, batch }] }]`, rows in merge order; under a profile's `external-scheduler`, `{ scheduler, note, repos: [] }`. Its `tips`: `gh` (whether CI could be asked), `ci` (true with `--gh`) and `repos: [{ repo, path, rows: [{ role, branch, sha, upstream, against, ahead, behind, pushed, issues?, ci? }], merged? }]`; a branch that is gone is `{ role, branch, sha: null, missing: true }`.
- **`resume --json`**: `goal`, `opened`, `lastActivity`, `archived`; `status` (the whole `status --json` object); `rulings` (`[{ date, slug, by, line }]`, in force only, `line` the ruling's first line; an answered question's ruling also carries `answer`, the line of its answer, which resume lists before `line`); `rules` (the rules whose scope is the loop, `[{ slug, scope, until, by, under, text }]`); `inFlight` (`[{ id, title, branch, worker, since, stale, mark }]`, and `next`, the step in words as `status.inFlightRows` gives it, where it is not the mark's own text: an acceptance line only the owner ticks waits before done, the issue is approved and carries no code or is worked in place, its recorded merge does not count for its code as it is now, a round sent it back and no row was recorded after it, or its approve is refused for its model; `mark` as in `status --json`; in progress and not waiting — as many as `status.inFlight`); `waiting` (`[{ id, title, status, after }]`, open or in-progress issues whose After is not settled — as many as `status.waiting`; an in-progress row also carries `branch`, `worker`, `since`, `stale`); `held` (`[{ id, title, priority, files, heldBy }]`, open issues a taken file holds back, and, with `questions` instead of a holder, those an open question names; `kept` (`[{ id, title, priority, kind, by }]` for an open promise, `{ …, kind, person, checkWhen, came }` for an open wait, `came` true once its proof is recorded, never offered); `held`, `kept` and `readyTotal` together are `status.ready`); `questions`, `proposed` (open questions of kind rule) and `ratify` (open asks, as in `status`); `next` (`[{ id, title, priority, noAcceptance? }]`, the first `--ready n`) and `readyTotal` (under a profile's `external-scheduler`: `next` and `held` empty, `readyTotal` null, and `scheduler` added); `queue` (above); `merged` (`[{ id, title, sha, repo, ci }]`, CI pending or red); `tips` (above); `uncommitted` (paths, or null outside the committed modes); `log` (the last `--log n` lines, without the leading `- `; null with `--log 0`); last, with `--as <who>`, `as` (the `next --as <who> --json` object).
- **`list --json`**, **`show <id> --json`**: the parsed issue (`list` an array of them) — `file`, `id`, `title`, `status`, `kind`, `priority`, `tier`, `tags`, `files`, `after`, `sources`, `fields` (every header field by lower-case name) and `sections` (every section's text by lower-case name); `show --json` also carries `evidenceRows`, each row with its ordinal `n` (the number `retract` takes), `ran`, `saw` and whether it is `retracted`, and is complete whatever the text view cuts.

## Loop metrics

`report` prints the loop's metrics before its lists of issues, `report --metrics` prints them alone, and `report --json` carries them under `metrics`. They are read from the record alone — the journal and the issue files, never git or a network — so they are as good as the record: a number the record cannot back says **no data**, with the reason in `noData` and null values, never a zero. An approve that names no reviewer has no standing, a loop with no merge has no CI after one. Every metric carries `n`, the issues it was read from; a closed issue is one in a status that closes the record (`done`).

- `check`: `{ declared, checks, landsOn, merges, byRepo }`. Where the repository has a check, the check decides what lands; a fresh reviewer can only stop a change, and its word is recorded as testimony. `goal.md` names the commands: a `Check: <command>` line for the whole loop, a `Check (<name>): <command>` line for one repository, `<repo>` being the name its Files prefix writes (`declared` and `checks` list them). A repository's declared check is its own `Check (<name>)` lines, else the loop's `Check:` lines. A merge carries the declared check when the `--ran` text of its merge line equals a declared command after trimming whitespace; a row with any other text, a merge with no row and a repository that declares nothing carry none. `landsOn` is `check` when every merge carries the declared check, `testimony` when none does, `partial` between, and `status` and `report` print the testimony mark for `testimony` and, per repository, `k of n merges carry the declared check`. `merges` is `{ merges, withCheck, noCheck, red }` over the merged issues, counted by each issue's last merge line: `withCheck` carries the declared check, `noCheck` does not (no row, or another command), `red` is `[{ id, cause }]` for merges landed with `--red`. `byRepo` is `{ <repo>: { repo, merges, withCheck, noCheck, red, declared, landsOn, k, n } }`, `k` the merges carrying the declared check and `n` all its merges, an issue naming two repositories counting in each; `status --group repo` and `report` print it.
- `cycleTime`: the first move into progress to the last close, per closed issue: `{ n, of, medianHours, p90Hours, maxHours }`. `leadTime`: the same from the filing.
- `rounds`: `round` lines and `changes` verdicts on the closed issues: `{ n, rounds, issuesWithRounds, changes, issuesWithChanges }`.
- `reopenings`: moves out of a closing status (done back to open or in progress), on every issue the journal tracks: `{ n, times, issues }`. Deferred or dropped work brought back is not a reopening.
- `slips`: `{ reopens, retractions, scopeGrew }`, each `[{ writer, coordinator, count, issues }]`: the reopens after done, the retractions of a row, a note or an approve, and the changes that grew a leased issue's acceptance, per writer — the `--by` of the call that wrote each line (`null` when it named nobody), `coordinator` whether that name reviews as the loop's director. A refused call writes nothing and is not counted.
- `freshReviews`: the standing of the live approve that cleared each closed issue — `{ n, recorded, fresh, coordinator, self, relayed, bot, unrecorded, share }`, a relayed fresh approve and a bot's counted apart from fresh, `share` fresh among those with a recorded standing; `code`, the same for the closed issues that carry code; `reviewers`, how many each fresh reviewer cleared.
- `batches`: the verdicts given on several issues at once, by their batch id, in the order of the log: `{ n, batches: [{ id, verdict, by, at, issues, size, rounds }] }`, `rounds` the red rounds recorded on its issues after it; the text prints them only when there is one.
- `redCiAfterMerge`: the merged issues whose CI was recorded red at any point after the merge, among those whose CI settled green or red: `{ n, settled, red, issues, share, pending, none }`.
- `followUps`: an issue filed within 7 days after a closed issue first closed, whose **Found by** names that issue's number (a reviewer's name such as `reviewer-450` counts; a number inside a sha does not): `{ windowDays, n, windowOpen, withFollowUps, windowClosed, windowClosedWithFollowUps, share, followUps: [{ id, followUps }] }`. A closed research issue is left out: the issues filed from it are its product. `windowOpen` counts the closes whose 7 days have not passed yet; `share` is taken over the `windowClosed` ones only, because a close whose window is still open has not yet shown it has no follow-up (null while none has passed).
