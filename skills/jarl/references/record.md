## Where the loop lives

Everything lives in `.jarl/` in the main checkout the loop runs in. On a feature branch it never
reaches `main`; opened as a permanent record it lives on, wherever `--root` names, for good. The
loop runs in one of three modes, chosen once at `init`:

- **Default — out of git.** `init` writes `.jarl/.gitignore` with two lines, `*` and `**/*`, so git never sees the loop: it stays out of the branch's history, its diffs and its merges. The loop exists only in the main checkout's working tree — it belongs to that checkout, not to the branch, and no other clone or worktree has it. A worker's worktree therefore sees no `.jarl/`, so the worker, the reviewer and the merger always pass the loop root (the directory that holds `.jarl/`) as `root` (`--root` on the CLI), and nobody ever commits `.jarl/`.
- **Committed — `init --committed`.** `.jarl/.gitignore` ignores only the tool's write lock and the temporary files a write leaves for an instant (`/.lock`, `/.lock.break`, `.*.tmp`), so a `git add` made while a call runs never commits them; the loop itself is committed with the work on the feature branch. `.jarl/.gitattributes` tells git how the loop merges when two branches carrying it meet: `log.md` by union (one dated line per event), `decisions.md` never by union but by Jarl's own driver, `jarl.mjs merge-driver decisions %O %A %B`, which keeps both sides' rulings block by block and stops with conflict markers when both sides superseded the same ruling, used one slug for two rulings, or rewrote one ruling. The tool configures that driver in the repository's local git configuration (a local command, never committed) at `init` and at the first write of a committed loop that lacks it, with a fallback to git's own conflict markers when the script is gone: a driver git is told to run but cannot start keeps ours and drops theirs without a word. A clone that never configured it gets plain markers. The merger passes the driver on every merge anyway (`merge-driver flags`); GitHub's merge button runs no driver, so a loop's branches merge locally. The merger commits `.jarl/` with every merge, and the last commit before the branch merges to `main` removes the whole directory.
- **Permanent — `init --permanent`.** Committed the same way, with the same narrow `.gitignore` — a record that must survive is always committed — and `init` additionally writes `.jarl/.permanent`, so a later session reads the mode from the loop itself rather than being told. This loop does not live on a feature branch at all: it lives wherever `--root` points, kept as a standing record, for example a repository that keeps one loop per release as that release's record, driving work in other repositories. Everything above — the files of the loop, the issue format, the roles, the tool — is the same; only closing differs, in [Closing the branch](jarl.md#closing-the-branch).

A loop whose `.jarl/.gitignore` ignores everything (a line `*`) is in the default mode; one without that
line, or with no ignore file at all, is committed, and one that also carries `.jarl/.permanent` is the
permanent mode. Only `init` decides the mode of a new loop. A committed loop without the narrow
ignore file is given it by its first write, which changes nothing about its mode; no command
ever turns one mode's ignore file into the other's.
`mode permanent` is the one exception: it turns an *existing, committed* loop into the permanent mode
in place, for a committed loop (one opened `--committed`). It refuses a default-mode loop (out of git): a permanent record must be committed,
and there is no in-place way to add git tracking to one, so start a fresh loop with `init --permanent`
instead. It refuses an already-permanent loop too, clearly, rather than silently doing nothing. See the
command table in [commands.md](commands.md#the-commands).

**A committed loop commits itself.** In the committed and permanent modes, `status` and `close` name how many loop files git has not committed and `resume` lists them (`git status` of `.jarl/` in the loop's repository). A loop whose code lives in another repository has no merge in its own repository to ride on, so without this the record in git contradicts itself. The count is silent in the default mode and outside a git repository.

## The files of the loop

The tool writes thirteen paths in `.jarl/`, listed below, and the temporary files (`.*.tmp`) a write leaves for an instant. It reads two things it never writes: the issue templates in `.jarl/templates/`, which the owner or the jarl writes by hand (`archive` leaves them in place, see [Templates](commands.md#templates)), and a `handoff.md` left in a loop, which `resume` names and `handoff read` prints, as history and never as state.

| Path | What | Who writes |
|---|---|---|
| `.jarl/goal.md` | Why this branch exists, in one paragraph; the standing assumptions; the rules that apply here. Written once at the start, amended only with the owner's word. A `Coordinators: a, b` line (plain, a list item, or bold) names extra reviewers who count as `coordinator` rather than `fresh`, alongside `coordinator`, `jarl`, `reeve` and the loop's own name — the directory holding `.jarl/` — which count as coordinators without being declared. Each name on the line is a coordinator, and its slice is the issues tagged `slice:<name>`: the part of the backlog it runs. Each issue is in one slice at most (`field Tags`, `new` and `import` refuse a second `slice:` tag), and an issue in none is the jarl's. A `Merger: <name>` line names the one holder that raises the merger, the jarl or one coordinator: every approve not yet merged, in every slice, is on it, so one merger at a time writes the main checkout. `Model (<tier>): <model-id>[, <model-id>…]` lines (the same forms, one per tier) say which models run on each tier: the first is the tier's default, the order of the tiers ranks the models, and a model on no line is unplaced (see [Which model sits where](models.md#which-model-sits-where)). A `Takeover: <rounds>` line sets the red rounds after which `round` prints the takeover block, for every kind of issue, and `Takeover (<kind>): <rounds>` sets it for one kind; a kind with no line takes the bare one, and a loop with neither takes three. The limit is read from the goal at each round, as the goal reads then, and the rounds are counted from the last takeover (or from the first round), so a changed limit takes effect at the next round, whether `goal --set` (which logs the change) or a hand edit changed it; each round's log line carries its standing in brackets right after its number (`<id> round <n> (count <k> of <limit>) · …`, or `(takeover <k> of <limit>)` on the round that takes over), where a writer that records no standing puts the separator, so no text of a round poses as one. A round line without a standing is read as the takeover its writer printed: such a writer reads no `Takeover` line and prints the takeover block at every round from the third, also where the goal sets another limit, and the count after its round starts again from the block it printed. A `Check: <command>` line (the same forms, one per check, several allowed) names the check that decides what lands — the repository's own test or gate — and a `Check (<name>): <command>` line names one repository's, `<repo>` being the name its Files prefix writes; Jarl never runs it. A merge carries the check when its `--ran` text (`merged --ran --saw`) equals a declared command; `status` and `report` say per repository how many merges carry it, and that the loop lands on testimony alone while none does or while the goal declares no check (see [Loop metrics](commands.md#loop-metrics)). | jarl |
| `.jarl/decisions.md` | Rulings: `## YYYY-MM-DD · slug`, the ruling, **By:** who ruled. New rulings are appended and a ruling's text is never edited; the one change the tool makes to a written entry is adding a line to its closing block: **Superseded by:** from `decide --supersedes`, which takes one ruling or several, and **Supersession withdrawn:** from `retract <slug> supersession`, which puts a ruling superseded by mistake back in force. Read before deciding anything; never re-derive a ruling that is here. A ruling marked **Superseded by:** is not in force — the one that superseded it is; `decisions --live` lists only the rulings in force. A rule with a scope (`decide --applies-to`) carries **Applies to:** as the first line of its closing block; a reader of formats 1 and 2, which knows no such field, reads that line as the last line of the ruling's text and every field after it in full, so a scope raises no format and works in every loop; offering a rule for promotion at close is a question of kind rule, which raises the loop to format 3. | jarl |
| `.jarl/issues/7-slug.md` | One issue per file, numbered in filing order from 1. A number is written plain (7, 42, 1000); a number written with leading zeros, as 007, is the same issue as 7. Format below. | jarl (header, status), worker (evidence) |
| `.jarl/log.md` | The journal, append-only, one dated line per event: filed, started, done, dropped, merged, asked, decided. A text of several lines never breaks a line: the whole of it is kept where it belongs (the issue, `asks.md`, `decisions.md`) and the line holds its first line and a pointer. | everyone, through the jarl |
| `.jarl/repos.md` | The repositories the issues name by name, one line each: the name, the repository's root commits (all of them), its origin as found and its base branch, and no path. Written only when an issue first names a repository by name, and by `base`; each write is a log line. | jarl |
| `.jarl/asks.md` | The questions for the owner, and the escalations a coordinator sends the jarl, one block per question: its type, the issue and the slice it names, its options and its answer; the ids are `a-1`, `a-2` and so on. | jarl (`ask`, `answer`) |
| `.jarl/profile.json` | The loop's profile, read as data (see [Profiles](profile.md#profiles)); written by `init --profile`. | jarl |
| `.jarl/archive/` | The archived loops, one directory `<yyyy.mm.dd>-<slug>/` each. | jarl (`archive`) |
| `.jarl/.gitignore` · `.jarl/.gitattributes` · `.jarl/.permanent` | The mode of the loop and how git merges it (see [Where the loop lives](#where-the-loop-lives)). | jarl (`init`) |
| `.jarl/.lock` · `.jarl/.lock.break` | The write lock (see [The write lock](#the-write-lock)). | every command that writes |

## The log is the record

**The log is the record, and one tool moves it**: `scripts/jarl.mjs` (Node, zero dependencies). An issue's status, its lease (Branch, Worker, Model, Since), its merge and CI state, its evidence rows and its verdicts are what the lines of `.jarl/log.md` say, read in order. The header fields of an issue file that show the status, the lease, the merge and the CI state are the tool's rendering of those lines, written in the same call, and every view and the done gate read the log. Every status change, tag, priority, ruling and log line goes through the tool, never through a hand edit — a status that changed without a log line did not change, and the tool is what makes that true rather than promised. A header edited by hand is never believed: it is printed as a disagreement (see [When a header disagrees with the log](#when-a-header-disagrees-with-the-log)).

**Every line names its writer.** Every write at the command line and through the tools passes `--by <who>`, and that name goes in a fixed place right after the stamp: `- <stamp> by <who> · <text>`, or after the key on a line about an issue (`- <stamp> key <key> by <who> · <text>`). The place is fixed, so no text of a line can pose as a writer. A library call that names nobody writes `unrecorded`, as a conversion does for the lines it carries over: a line with that writer stands as no holder of a lease and no name beside it. On a verdict, an answer, a ruling and a retraction `--by` is who gave it.

**A line about an issue names the issue's key.** `new` gives every issue a key, its filing stamp without separators and four random letters (`20261103T2044-kqvd`), written in the header as `**Key:**` and in its fixed place right after the stamp, before the writer, on the filed line and on every later line about the issue: `- <stamp> key <key> by <who> · <text>`. The key, not the number, says which issue a keyed line is about: two copies of the loop that each filed an issue under one number keep their lines apart after the merge, and `renumber <id> --key <key>` gives one of the two files a free number with every line written about it kept and none rewritten, adding one line, `<new> renumbered from <old> · issues/<file>`. A line with no key is read by its number. The key is the tool's: no profile declares a field of that name, and `field` does not write it.

## The description and the history

Each side of an issue, its description and its history, has one rule.

**Every part of the description can be changed, and every change is logged.** The description is what the work is: the title, **Priority:**, **Tier:**, **Kind:**, **Found by:**, **Tags:**, **Files:**, **Repo:**, **After:**, **Parent:**, **Source:**, **Where:**, **Resources:**, the fields a profile declares, and the What, Why, Acceptance and Changelog sections and the sections a profile declares. One command changes it, `field <ids> <name>`, for every part: a value replaces the part, `--add` and `--remove` change the items of a list field (`--add` also adds to a section), `--clear` empties it. Each change writes one log line per issue and part with what the part held before, and with who changed it when `--by` names someone (a write that names nobody carries no author, never a name nobody gave): `<id> field <Name> · <value> · was <old value>[ · by <who>]` for a header field, `<id> body · <part> · was "<old text>"[ · by <who>]` for the title or a section. The old title is kept whole; an old section by its first line (at most 120 characters) and its length, `was "<first line>" (<n> characters)`, and an old or a new **Where:** longer than 120 characters by its first 120 and its length, `<first 120 characters>… (<n> characters)`. A value stays on one line, a line break written as ⏎ and the log's separator `·` as `∙`. A part given the value it already holds writes no line. `field` refuses any other name, naming the fields it writes and the command that writes that one. Through the record library, `setField`, `setBody`, `setRepo` and `setAfter` take the writer as `opts.by`; `setTags`, `setPriority`, `setFiles` and `setSource` take no options, and their changes carry no author; `setField` writes Tags, Priority, Files and Source by name, as `field` does, with `opts.by` as the writer. No reader takes a description line as state: `log` writes a hand-written line of the `field` shape as a note, as it stands, and only the commands keep such lines true.

**Nothing in the history is ever changed.** The history is what happened: the moves, the lease, evidence rows and notes, verdicts, merges and their CI, rulings and answers. The status and the lease move only through `set`, which keeps its rules; a merge and its CI are recorded by `merged`. Evidence, verdicts, merges, rulings and answers have no edit command at all: an evidence row or an approve is taken back by `retract`, which strikes it through and appends who and why, and a ruling is replaced by `decide --supersedes`, which leaves the old one in place, marked.

## When a header disagrees with the log

What the log says of an issue is folded in file order, the way the commands write it. The status is the target of the last move (the filing counts as a move into the profile's first status). A move into a status that holds the lease sets Since to the line's stamp, replaces Branch when the line names one, replaces Worker when it names one (and then Model with the line's own, or none), and replaces Model alone when only a model is named; a move into any other status removes Worker, Model and Since and keeps Branch. A merge line sets Merged and Merge check (the check and what it printed, none when it names none) and takes that line's CI state, none when it names none, and a CI line replaces the CI state alone. `set` and `merged` write the line first and the file second, with one stamp for Since and its line, so a write that stops between the two leaves the log ahead of the file and never the file ahead of the log.

**Where the file says something else, the log wins and the view says so.** `status`, `resume` and `show` print one line for each of Status, Branch, Worker, Model, Since, Merged, Merge check and CI whose header differs from the log, and no count, mark, offer, queue row, report row or gate decision follows the file:

`record: 7 Status reads done in the file and in-progress in the log, which is the record — to follow the log, write **Status:** in-progress back into the header; to make the file's value the record, jarl.mjs set 7 done (a move into done, through its checks)`

`set <ids> <status-in-the-log> --header` rewrites the header fields the log renders from the log, writes no log line and is never a move; it settles every line of an issue at once (a write that stopped between the log and the file is repaired by it, and the move stays recorded). Writing a header back to the log's value by hand settles its line too. The command the line names for the other direction is a real change of the record and writes a line of its own: `set` writes a move line (and, in a lease, stamps Since again), `merged` writes a merge line, `merged <id> --ci <ci-state>` a CI line. The Since field has no command of its own, so a header Since that differs is only written back. A line that is printed for a field the log has no value for says the header should lose it. An issue the log holds no filing and no move of (a file made by hand, or one the log knows only by merge or CI lines) reads its header as it stands and is printed as not in the log; `set <id> <status>` puts it there. A hand edit of a profile's status list changes which past lines read as moves: a line of the shape the tool writes for a move (`<id> → <status>`, the status a lower-case word) into a status the list does not name reads as a note, and `status` prints it once and follows the list as it stands. Any other line with an arrow is a note and is never printed. A move line is read by position: after the status come the free reason, never searched for fields, the segment `handover` on a move that hands the lease over (it follows the reason, which a handover always has, so a reason alone is never read as one), and the lease fields in the order `set` writes them (branch, model, worker, worktree); a reason that opens with a lease field's name is closed by a `(reason)` segment, and the reason of a move that opens with a lease word is read as the tool wrote it; lines written before the marker follow the comma rule, where a `worker` or `model` text with a comma is a sentence and one without is a name, so an old reason that is only `branch <word>` or `worker <name>` reads as the lease field. `set` refuses a worker or model with a comma, a branch git would not accept (a space among the characters it refuses) and any lease value on more than one line, so every value it writes reads back identical from the log and from the header. `set --header` restores no `Deferred:` or `Dropped:` reason under Evidence; the reason stays in the log line.

**The file is the authority for everything the log does not hold as state**: the title, Kind, Priority, Tier, Tags, Files, Repo, After, Parent, Source, Where, Resources, Found by, a profile's own fields, Worktree and the text of every section. The lines `after …`, `source …`, `field …` (Resources and a profile's fields) and `body …` that their commands write are an audit of the change, and nothing reads them as state; the one time read from them is when an issue joined its parent, as a parent's own check counts only after its last sub-issue closed or joined it.

**A Branch the log has recorded cannot be cleared.** Branch stays after the issue leaves in-progress, as the record of where the work was done, and it marks the issue as carrying code. A Branch recorded by mistake is replaced by the right one with `set <ids> in-progress --branch <worker-branch>`; no command removes it, and a hand edit of the header that removes it is printed as a disagreement and changes nothing.

**In a committed loop**, git merges `log.md` by union, which places the lines of two branches in the order of the merge direction. When both branches moved one issue, the clone that merged one way and the clone that merged the other way hold the same lines in two orders, and each folds its own log: the later move in its file decides, which is the order the done gate replays. The issue file has no merge driver and conflicts on the changed header lines; a resolution by hand that differs from the log the clone holds is printed as a disagreement, and writing the header back settles it. Two clones that hold the same log text read the same. A conflict git leaves in an issue file is refused by `verify`; text written into an issue gets a backslash in front of each line that reads as a conflict marker (`<<<<<<<`, `=======`, `>>>>>>>`), which renders the same and is never taken for a conflict, and a hand edit that quotes a conflict does the same.

**The log's own door is shut to forged state.** `log` writes a note, and a line that starts with an id and an arrow, or reads as a filing, a move, a round, a verdict, a retraction, an evidence row, a branch tip, a merge, a CI state, a body change, the owner's tick of an acceptance line or its retraction is refused, with the command that writes it. A composer's `record.appendLog` is refused the same way, and `record.writeAtomic` writes any file but the journal whole. A well-formed line written into `log.md` by hand cannot be told from a real one; only the commands keep the lines true. A tip line carries the tip mark in its fixed place before the separator, after the key and before the writer (`- <stamp> key <key> tip by <who> · <id> tip <sha>`), which only the write of a row, a verdict, a merge or a close puts there, and it is read only right after the line its own write made, under the same stamp. A line of the tip's text without the mark is the tip of nothing, wherever it stands and whoever wrote it (a log command that writes `- <stamp> · <text>` cannot write the mark), and `verify` names it. The first tip line raises the loop to record format 3; a loop that records no tip is not raised for it, and in a loop a composer keeps below format 3 no tip is written.

## The write lock

Every command that writes holds `.jarl/.lock` while it runs, and every file is replaced whole, so the workers, reviewers and the merger can all call the tool at the same moment — through the tools or the CLI, from one session or several — without losing each other's rows, log lines or issue numbers. One server runs its calls one at a time, in the order they came, so a call waiting on the lock, or a slow `resume`, delays the next call to that server; against every other writer (another session's server, a CLI call) the lock decides. A lock is taken over when its holder is gone: on the same machine, as soon as the holder's process is not running; a lock left empty (the holder died between creating and filling it) after 2 seconds; a lock from another machine sharing the checkout, or one whose holder cannot be read, only after 30 seconds; and a lock whose process id is running again, against a reused id, after 10 minutes. A call waits at most 20 seconds and then fails with nothing written, naming the holder: retry it. So the first call after a crash on another machine can fail once before the 30 seconds pass, and one after a reused process id waits out the 10 minutes or needs the lock removed by hand. Breaking a stale lock is itself serialized (`.jarl/.lock.break`), so it never hands the lock to two callers. Never delete the lock by hand while a call may still be running.

## The issue file

```
# 7 · title

**Status:** open | in-progress | done | dropped | deferred
**Kind:** bug | gap | cleanup | docs | test | research | process | promise | wait — the last two are kept, not worked: a promise is kept by whoever its **Found by:** names, a wait is held by its **Person:**; `next` never offers either to a worker, and either ends when the issue closes (see [What is on whom](commands.md#what-is-on-whom))
**Priority:** 1 | 2 | 3
**Tier:** light | standard | strong, weakest first — the tier of model the worker is raised on, explicit in the file, never implied; the loop's `Model (<tier>):` lines in `goal.md` say which models run on each tier, and the criteria are in [Which model sits where](models.md#which-model-sits-where)
**Tags:** comma, separated
**Files:** the files it touches, comma separated — what `next` uses to keep workers apart; when **Repo:** is set, each starts with that repository's directory name (`tool/src/a.mjs`)
**Repo:** only when the code lives in another repository than the loop — its name, or the path to its main checkout where it is not a sibling of the loop's (see [Code in another repository](repositories.md#code-in-another-repository))
**After:** only when it waits on other issues — their ids; `next` holds it until each is done or dropped
**Parent:** only on a sub-issue — the id of the one issue it is a sub-issue of (see [Filing](jarl.md#filing))
**Resources:** only when the work uses something no other work may use at the same time — names, comma separated, loop-wide and not files (a port, a database server, `gate` for the machine's load); written with `field <ids> resources "gate, db"`, and emptied with `field <ids> resources --clear`. `next` and the lease read it: `next` does not offer an issue whose resource an in-progress issue holds, nor two issues that declare the same one at once, across repositories too, and `next --all` names the holder under *held by a resource another issue holds*; a lease on such an issue is refused, naming the holder (see [Packages and leases](repositories.md#leases)). A resource is held for a lease's whole life: there is no capacity and no lock at run time, `scope`, the merge queue and the file rules never read it, contention during a test run belongs to the repository's own harness or the workspace's run lock, and how many heavy workers run at once stays the jarl's choice. `Resources` is a field Jarl writes itself, so a profile cannot declare a field of that name.
**Found by:** who, doing what; on a promise, who made it and keeps it
**Person:** · **Check when:** only on a wait (written with `new --kind wait --person "<name>" --check-when "<date-or-event>"`, or by `field`) — the outside person it is held by, the name `next --as` answers to, and when to check it, a date or the event to check after; neither is emptied while the issue is a wait
**Source:** only when it comes from research — <report dir>#<finding id>, several comma separated
**Where:** file:line, or the command and what it printed
**Branch:** only once it is in progress with --branch — the worker branch it is done on, shared by a package; kept after done
**Worker:** · **Model:** · **Since:** the lease, only while in progress — who, on which model (only when `--model` was given), from when (UTC); the lease records no worktree, which is found through the branch (a lease that holds a **Worktree:** field keeps it until it ends or is handed over)
**Merged:** · **Merge check:** · **CI:** only once `merged` records it — the sha (and where), the check that decided the merge and what it printed (only when `--ran`/`--saw` were given), and pending | green | red | none

## What
One paragraph: the fact.

## Why
What it costs if left as is.

## Acceptance
Checkable. A test name, a command and its expected output, a sentence that is true or false.

## Changelog
Only when the change is user-visible: `- Added: …` (or Changed, Deprecated, Removed, Fixed, Security), one line each.

## Reviews
Written by `review` and `retract`: one entry per verdict — `approve`, `changes` or `retract`, the reviewer and its standing, the date, then the whole findings or reason. Before Evidence, which stays last.

## Evidence
Filled as the work goes: ### Proof, the worker's rows of what was run and what it printed; ### Notes, what only explains.
```

These are the built-in statuses, kinds and tiers. A loop opened with a [profile](profile.md#profiles) carries the statuses, kinds, tiers, fields and sections its profile names instead.

`dropped` and `deferred` always carry a reason under **Evidence**, in Notes, after whatever was already written there. A `research` issue produces a written result
and files new issues; it never edits code.

## The format marker

The record's format is one machine line of `goal.md`, `Format: 4`, written by `init` and by nothing else. Jarl reads a loop that holds exactly that line and refuses any other, or none, on every command, before anything else is read, naming [converting-from-6-2.md](converting-from-6-2.md), which an agent follows to convert a loop of the format before. No command changes the line, and there is no other format to read: an archive under `.jarl/archive/` is read by `models --archives` as it stands, its lines the tool does not place left out.

## What only the command line does


The library and the command line write the same files and log lines for every operation of the record, except the rows of this table. Each row is one difference that stays, with what the command line does, what the library does and the reason. The rows are the one list; a test in the suite holds this table to it.

| Item | Command line | Library | Why |
|---|---|---|---|
| Merge with no CI state | records no CI state unless `--ci` is given | records `pending` when a sha is given without a CI state | a composer that records a merge before CI has run says so in the record; a person at the command line gives the state when it is known |
| Numbers of issues and questions | writes them plain (`3`, `a-1`) | writes three digits (`003`, `a-001`) | a composer's files sort by name, and the contract returns the three-digit ids |
| Merge cleanup | removes the merged issue's worktree and local branch when that is safe, unless `--keep` is given | removes nothing | removing git worktrees and branches is a step a person asks for at the command line; a composer removes the ones it made |
| Caller of a status or field move | asks as `cli`, so a status the profile marks `set-by: record` is refused | asks as `record` unless `caller: cli` is passed | a status the profile gives to the record's own tool is moved by the composer that runs the loop, not by a person at the command line |
| Worktree of a lease | refuses a `--worktree` that exists and is not a worktree of the lease's repository, or has another branch checked out | accepts it and stores nothing | the worktree of a lease is found through its branch; a composer that tracks worktrees checks them itself |
| Base of a done check | checks a done against the branch checked out in the merge's repository, and takes no base | takes `base`, the branch or ref a merge landed in, for a composer that lands into a branch not checked out | a person's merge lands in the checked-out branch; a composer names its own target, and no command-line call can name one |
| Who answered | records `--by`, which it requires | records the owner; the contract's answer takes no name | a composer cannot name the ratifier through the library, because the answer keeps the arguments the contract names |
| Who ruled | records `--by`, which it requires | records the coordinator unless `by` names another | at the command line the author of a ruling is said, never assumed; a composer calls as the coordinator of its loop, which the contract's decide records when it names nobody |
| Ratified area rulings | writes the type's decision log and the rule's log through the Yggdrasil edge | returns the entries and writes neither | the Yggdrasil write is the only call from Jarl to another family tool; a composer writes into its own graph; no twin case exists, because it needs a loop with an area ruling and a graph |
| Replies and notes | prints notes and replies that depend on the caller: the goal that names no check or no Model line (`init`), the offer of the Model lines (`set`; the log lines that remember it are written by the library too), the tier of a new issue (`new`), the lease notes (`set`), the proof and fresh-review notes (`merged`), the model and proof notes and the next step (`review`), the owner's word with no question (`decide`), and a long free-text note (`evidence`) | writes the same files and log lines, and prints none of them | the notes are for a person at the command line; the twin cases compare files and log lines, and a note is neither, except the lines that remember the offer of the Model lines, which the twin cases compare |
| Lists of ids | takes a list of ids (`12,13`, `203-206`) for `field` and `round`, and checks every id before it writes one | `setBody`, `setFiles`, `setRepo`, `setAfter` and `setSource` take one id each | a person at the command line writes a package of issues in one call; a composer calls the operation for each id it holds and decides what a refusal on one of them means; no twin case exists, because the twin loops run one id |
| Count of findings of a round | records the count of findings a round left, given with `--finding-count <n>` | `addRound` records the round with no count, and a takeover block shows a dash for it when another round of the issue has a count, and has no findings line when none has | the contract's addRound keeps the arguments it names, so the count is given at the command line |
| The verbs `retract` and `field` | retracts an approve or an evidence row with `retract`, and writes every part of the description with `field`: a value, `--add`, `--remove` or `--clear` | retracts with `review` (verdict `retract`) and `addEvidence` (`retract`); `setBody`, `setTags`, `setPriority`, `setFiles`, `setRepo`, `setAfter`, `setSource` and `setField` each write their part whole, and `setStatus` with the name `resources` writes Resources; a field is emptied with an empty value | the verbs are the command line's grammar over the operations; the library keeps the operations its contract names |
| `base` | changes the base branch a declared repository is held against | no function | a repository is declared by Jarl when an issue first names it; a change of its base is a decision of the person who runs the loop |
| `close` | ends the loop: removes it, or keeps it as a permanent record | no function | ending a loop belongs to whoever runs it, and a profile may hand that to a composer |
| `archive` | moves the loop under an archive directory and leaves the open issues named | no function | ending a loop belongs to whoever runs it, and a profile may hand that to a composer |
| `mode` | makes the loop permanent, a mode of git | no function | the mode is written at init, and a change of it is a decision of the person who commits the record |
| `import` | files issues from a Markdown source | no function; newIssue files one issue | filing from a source is the composer's choice |
| `next` | lists the open issues that can start now, and with `--as` what is on one holder (which `status --as` and `resume --as` end with) | no function; statusData carries the counts, and neither statusData nor resumeData takes `as` | ordering work is a composer's planner; Jarl offers what can run now, and says who moves next |
| `tick` | records the owner's tick of an acceptance line only he ticks | no function | the owner ticks at the command line or through the tools |
| `report` | writes the loop's text report with its metrics | no function | a summary for a person; a composer reports from its own record |
| `scope` | reads a worker branch's diff against the files its issues declare | no function | it reads git; a composer's gate decides what lands |
| A command or a flag the surface does not have | refuses it with its reason and, on the last line, the call doing what was asked | no command names, only functions called by name | a person or an agent guesses a form; a composer calls a function by its own name |
| The ready line of a refusal | ends every refusal with the form of the command that does what was meant, a `<placeholder>` where each value only the caller knows goes, refused when pasted as printed (a step to take first is a command on its own line); it never names a value Jarl chose, nor an act that is someone else's | refuses with the same reason, and the last line of its message writes the fix out in words: the flag or the argument to give, with the same placeholders | a composer makes no command-line call whose form could be printed, and acts on the reason in its own code |
| CI of the tips | `resume --gh` asks gh for the CI of each pushed tip | `resumeData` asks with `ci: true`, the key its contract has always named, or `gh: true`, the same | the command line names the flag after the program it runs, and `--ci` is merged's CI state; the contract keeps its key; no twin case exists, because gh is not run in the twin loops |
| `branches` | lists each branch with the issues it carries and its state | no function | it reads git in the repositories the issues name; a view for a person |
| `verify` | checks the record with its own readers in strict mode | no function; the readers are the library's | a consistency read for a person; a composer uses the readers |
| `models` | shows, per model, what the record holds as worker and as reviewer | no function | a reading of the record for choosing models; a view for a person |
| `goal` | reads or sets the goal line | no function; initLoop writes the goal | the goal is written at init; a change of it is a decision of the person who runs the loop |
| `show` | shows one issue as text, with its evidence rows and where its branch sits | no function; findIssue returns the same record as data | text for a person |
| `list` | lists the issues as a table | no function; loadIssues returns the same record as data | a table for a person |
| `changelog` | shows the changelog fragments of issues as text | no function | the release step writes the release text once, from the fragments |
| `handoff` | prints what `resume` prints, then the handoff file the loop holds, if there is one; its `write` writes nothing | no function | the handoff file is for a person to read at the start of a session |
| `sources` | lists the sources of issues | no function; setSource writes them | a view for a person |
| `profile` | shows the profile in use, as text | no function; loadProfile and describeProfile return it as data | text for a person |
