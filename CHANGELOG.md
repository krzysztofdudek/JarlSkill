# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Up to 0.1.0 Jarl followed Semantic Versioning on its own number. From 6.1.0 it follows the Yggdrasil family's one-number policy instead: the core of the family (Yggdrasil, Grain, Jarl and Horde) ships together under one number, so a minor release can include changes that ask something of you, and its section lists them under **Before you upgrade**. A release in which Jarl does not change says "No changes in Jarl."

## [Unreleased]

### Added
- A loop can require files before an issue is done, such as a picture before a fix and one after it. The loop's profile says which kinds of issue need which files and where they lie, `evidence <id> --file <path> --slot <name>` records a file, and `done` refuses until every required file is there and unchanged. Jarl copies nothing, and `show` and `verify` report the files.
- A new read-only command, `verify`, checks a loop's record for lines Jarl cannot read, headers that disagree with its log, repositories the issues name that are not on this machine, and open issues that cite a ruling that has been replaced. It changes nothing, and it exits with status 2 when it finds something.
- `models --with <root>` (repeatable) reads another loop, a loop's root or an archived loop, and `models --archives` reads the loop's own archives. The loops merge into one table grouped by the model as recorded, and the output names the loops it read, so a model can be judged over several loops instead of one. A path that is not a loop is refused and nothing is written.
- The record keeps which model did each piece of work. `set <ids> in-progress --model <m>` records the model the worker was raised on and `review … --model <m>` the model the reviewer was raised on, as the platform names it, with `@<effort>` where the platform has an effort setting. `review --relayed` marks a verdict that someone other than the reviewer recorded in its name.
- There are now three tiers, `light`, `standard` and `strong`, weakest first; `standard` stays the default. `new` without `--tier` says on the command line which tier it recorded and what each tier is for, and the takeover block after three rounds says to raise the fresh worker one tier up or on another model. A loop can name its models per tier in `goal.md` with lines such as `Model (strong): <model>, <model>`; the first is the tier's default, and a model on no line is unplaced. In such a loop, a lease or verdict without a model, an approve by the worker's own model and an approve by a lower-ranked model are noted on the command line, never refused.
- `models` shows, per model as worker and as reviewer and per kind of task, how often work passed first time, how often reviews were checked and missed, and says `fits`, `below`, `new` or `may clear` once there are five cases. Shares appear only from five cases; work with no recorded model is grouped by tier. `next` and `resume` show each ready issue's tier model and suggest a lower-ranked model that has fitted that kind of task. `resume` and `status --json` show the model of each issue in flight, or that none was recorded.
- A loop now records which format it was written in. When Jarl first writes something an older Jarl would read wrongly without saying so, it marks the loop first, and the older Jarl then refuses the loop with a clear message instead of misreading it. Loops that never need this stay as they are and keep working with older versions.
- A wrong verdict or evidence row can now be taken back without editing the record. `retract <id> review --by <who> "<reason>"` retracts the newest approve not yet retracted, and `retract <id> <n> --by <who> "<reason>"` retracts the n-th evidence row. The original stays in the issue, struck through, with an entry saying who retracted it and why; `done` and the metrics no longer count it. A retraction only tightens: it never retracts a `changes` verdict. The first retraction in a loop marks the loop for the newer format, so an older Jarl refuses it instead of still counting the retracted approve or row.
- `status` and `resume` now mark each issue in flight with one fact the record already holds, and say what comes next: no evidence rows since the start; rows and no verdict since the last start or round (it waits for a reviewer); changes requested; approved and queued. `--json` carries it (`inFlightRows` in `status`, `mark` on each `resume` row). No new status. `set <id> ready` (or `review`) is now refused with a message that names these views and says a loop can declare its own review status in its profile.
- An issue can declare exclusive resources, `field <ids> resources "gate, db"` (header field **Resources:**, loop-wide, names rather than files): `next` never offers an issue whose resource an in-progress issue holds, nor two issues that declare the same one, even in two repositories, and `next --all` names the holder. A resource is held for the whole lease; nothing else reads the field, and Jarl 6.1.0 ignores it. A profile cannot declare a field named `Resources`: Jarl refuses it, and says to rename the field. `list --match Resources=…` works.
- `status --tag <t>` shows status for the issues carrying one tag: the counts, in flight, stale leases, waiting, merges waiting on CI and the questions that name those issues. `--json` has the same shape. A tag no issue carries is refused.
- `body <id> --title "<title>"` changes an issue's title, with the old title in the log; the file keeps its name.
- `status`, `report` and `resume` list every closed issue whose done gate does not hold on the record (a retracted approve or proof, a merge after done or on a dropped issue, a code issue done with no merge), one line each with the command that repairs it. `report` now says "retracted" for a retracted approve.
- `show <id>` now prints an issue as the done gate sees it: the header, What, Why, Acceptance and Changelog, every evidence row and verdict since the last start or reopen, every `changes` finding no later approve has answered, one line for each earlier round, and last the call that prints everything. `show <id> --full` prints the whole file. Every evidence row carries its number (`[3]`), the number `retract` takes; `show --json` stays complete and adds the numbers.
- A free-text evidence note that runs long is now noted on stderr (command line only): it is still written whole, nothing is refused or cut, and the note points to `--ran`/`--saw` rows for proof of work.
- A merge now records the check that decided it. `merged <ids> --sha <sha> --ran "<check>" --saw "<summary>"` keeps the check and what it printed with the merge of every issue, in one call. That check is the merger's: it is not the worker's proof, so `set <id> done` still asks the worker for an evidence row, says so when it refuses, and `merged` says it when an issue has none. `merged <ids> --sha <sha> --red <id>` records a merge that landed while its check was red for a cause outside the branch, which issue `<id>` tracks; it is never counted as a passing check. `Check (<repo>): <command>` lines in `goal.md` name each repository's command. `status --by repo` and `report` show, per repository, how many merges carry the declared check, how many do not and how many landed on red with their cause. `init` says once when the goal names no check.
- The reply of `review` names the next step. After an approve of code it is the merger's one `merged <id> --sha <sha> --ran "<check>" --saw "<summary>"` call and then `set <id> done`, which a worker never does; after `changes` it is the round that sends the work back to a worker raised again.
- `merged` cleans up after a recorded merge. On the command line and in the tools it removes the issue's worktree and its local branch (`git worktree remove` and `git branch -d`, never a force, nothing pushed) when that is safe, and says what it removed or why it kept it: the branch is the base or a release branch, its tip is not in the base or the merge, another issue still holds a lease on it, its worktree has uncommitted or untracked files, is checked out elsewhere or is not on this machine, or git refuses. `--keep` skips it. A library caller gets no cleanup.
- An issue keeps the worker's proof apart from its notes. The `--ran`/`--saw` rows go under a **Proof** heading in the issue, and notes, rulings, reasons and retractions under **Notes**; an issue that already has evidence is left as it is. The merger's check is kept with the merge (**Merge check:**), so it never stands in for the worker's proof: `set done` still asks for the worker's row, and says so when it refuses. Two limits: a tool that does not know the headings and records a merge check as a row still gets a counted row, and a program such as Horde may keep its merge check in the proof on purpose.
- A question can offer its choices: `ask "<question>" --option "<label>: <effect>"`, repeated for each one, prints them ready for the choice window. `answer <id> --option <label>` records the choice made, and the ruling marks it among the options; an answer in the person's own words is recorded as his words.
- Several ratification questions are answered at once: `answer 2,3,4 yes --by <who>` gives one answer to all of them, and each gets its own ruling, naming the others it was answered with.
- `decide --supersedes` names the open issues that still cite the ruling it replaces, and a ruling by the owner with no question behind it gets a notice on the command line.
- `goal` prints the goal. `goal --set "Check (<repository>): <command>"`, `goal --set "Model (<tier>): <models>"` or `goal --set "Coordinators: <names>"` changes that one line of the goal and logs what it was and what it is now, so a change to what the loop runs is traceable.
- Repositories can be named. An issue's repository is written as its name, such as `Grain`, when its checkout stands beside the loop's checkout; otherwise it keeps its path and a note on the command line says why. Jarl records each named repository once, with its identity and its base branch and no path, so the record holds nothing that belongs to one machine; `repo --base <name> <branch>` changes the base, and every change of `repo` is logged. The first name marks the loop with its format, and a Jarl that does not read that format refuses the loop instead of misreading it.
- `--repo` takes a name, a checkout, a worktree or a file inside a repository, and always means the repository's main checkout.
- `show` and `status --by repo` print where each repository, and the worktree of a lease, is on this machine. `status --by repo` also prints each repository's base and warns when its checkout is on another branch. A name with no checkout on this machine says where to put one, and the commands that act on it refuse it.
- `check` on a branch now lists each added line that cites a loop issue by its number, so a stale reference shows before the merge. The check passes or fails as before.
- `branches` marks a branch that holds commits but no issue with `NO ISSUE`. A check of such a branch says how many commits it carries and what to file before it can run.
- The skill lists every difference between the record library and the command line, with the reason for each, so a tool that builds on the library can see where the two differ.

### Changed
- The skill is now a short entry file with a `references/` directory beside it. A plugin install gets both. If you copy the skill by hand, copy the whole `skills/jarl/` directory, not only `SKILL.md`.
- The skill uses one word for each concept and has a short glossary of them.
- The person who rules over a loop is called the owner.
- The claim an issue holds while it is in progress is called a lease. A profile that still writes the old flag name, `holds-claim`, keeps working.
- `tips` labels worker branches as worker branches, and the branch you are on as the feature branch.
- `profile` shows `lease` where it showed `holds-claim`.
- The command that measures a branch has the clearer name `scope`; `check` keeps working under its name.
- `set` changes statuses, and a new `field` verb writes the other fields, the fields a loop's profile declares and Resources. `field <ids> <name> --clear` empties a field, Files, Source, Where, Tags, After and Repo included. `files`, `repo`, `after`, `body`, `round` and `source` now take several issue numbers at once, such as `3,5-7`, and the call changes all of them or none. `jarl --help` now exits 0. Writing a field with `set <ids> <field> "<value>"` and emptying one with an empty value still work, and print the `field` form to use instead.
- A lease holds a branch, a worker and a start time, and no worktree path: the worktree is found through the branch. `set --worktree <path>` checks that the path is a worktree of the issue's repository with the lease's branch checked out, refuses it otherwise, and stores nothing.
- An answer to a ratification question must say who gave it, with `--by`; the command refuses a coordinator's name there, because the answer is the person's own ruling.
- New issues and questions are numbered plainly: 7, not 007. Issues already in a loop keep their names and numbers, and 007 and 7 mean the same issue everywhere, so you can type either.
- `merged --sha` on the command line records a CI state only when `--ci` is given; it no longer writes `pending` by default (a library call keeps `pending`). `set done` no longer notes a missing CI state for a merge that carries its passing check or its red landing.
- `status` and `report` say per repository how many merges carry the declared check ("1 of 3 merges carry the declared check"), and show the testimony mark for a repository that declares none. A merge carries the check when its `--ran` text equals a command a `Check:` line of `goal.md` declares; a merge with any other check row, or none, does not. The `check` object of `status --json` and `report --json` carries `merges` and `byRepo` besides `declared`, `checks` and `landsOn`.
- `next` now lists only the issues ready to start: no file held by work in progress, every `After` issue settled, and no open `stuck` or `stop` question on the issue. `next --all` adds the others under headers (held by a file and by whom, waiting on `After` and on what, held by an open question), and `next --json` rows carry a `group`. An issue with no declared files is marked `(no files declared)`. `resume` lists an issue held by an open question under Held.
- `review` now refuses findings of fewer than three words (`ok`, `-`, `LGTM`) and says how many it got: a verdict needs a few words about what was read and what was found.
- `new` now refuses a What, Why or section text that holds a matched opening and closing tag named after one of the issue's own fields (for example `<why>…</why>`) outside code, and says to pass that field in its own parameter; a lone tag, or a pair in backticks or a fenced block, is accepted. Its reply lists what was filed (priority, tier, kind, tags, acceptance lines, the length of What and Why) and each field left empty with the command that fills it.
- An issue moved from done to deferred or dropped, back to open and then to done (or from done to deferred and straight back to done, which is refused the same way after the reopen) needs a new `--ran`/`--saw` evidence row recorded after the reopen, as well as a new approve; a close that rests on a row from before the reopen is refused. A start or a reopen resets both; a red round spends only the approve.
- `close` refuses while any issue is deferred, in every loop it would remove (the default and the committed modes), and names the two ways forward: `archive` to keep the work, or `close --force` to remove it. A permanent loop keeps its directory. In a loop kept out of git, `close` leaves `.jarl/archive/` in place and says so. In a committed loop, `close` refuses while `.jarl/archive/` holds anything, so the archive does not reach the branch that merges to main: move it out of the tree, or use `close --force`, which removes the whole directory. `close --force` is described in the skill.
- The log is now the one record of an issue's status, who works on it, its merge and its CI state; the lines in the issue file are a copy the commands write beside it. Editing one of those lines by hand does not move the issue, change a count or let it close; `status`, `resume` and `show` print one line for each edit, saying how to put the file back or how to make the edit a real change.
- `log` refuses a line that looks like a move, a review, an evidence row, a merge or another line the record is made of, and names the command that writes it; a plain note is still accepted.

### Fixed
- A mention of another issue inside a note is no longer counted as a round of that issue.
- A `--worker` or `--branch` value that holds ` · ` is now refused, so a name can no longer be read as a model.
- A text of several lines given to a command is no longer cut to its first line. `review` writes the whole findings into the issue's new Reviews section (a second Important is no longer lost), a question keeps every line, and the answer or ruling that settles an issue points at the whole ruling instead of repeating its first line; `evidence` rows and titles keep every line too. The log stays one line per event: a short line and a pointer, or the lines joined when the text has no other home. Older Jarl versions still read such a loop.
- `status`, `resume` and `branches` no longer report a worker's worktree as gone when it lives somewhere this machine cannot see, such as a devcontainer. Jarl asks git which worktree holds the lease's branch (and uses the stored path only for older leases), and calls a worktree gone only when its directory was removed here; `branches` shows whether a worktree is here, elsewhere (locked) or not visible from here, and never marks a branch `DONE → delete` while the uncommitted changes in its worktree cannot be counted.
- `new` run from a linked worktree of a committed loop now refuses and names the main checkout to file from, and the number it takes is the highest over the main checkout and every linked worktree, so two workers filing in their own worktrees no longer get the same number.
- A loop can now hold 1000 issues or more. Issue and question numbers grow past 999 (1000, 1001); filing, listing, showing, ranges such as 998-1002, reviews, the journal, branches named `jarl/1000-…` and questions such as a-1000 all work, and numbers are ordered as numbers, so 999 comes before 1000. The first issue or question numbered 1000 or more marks the loop for the newer format, so an older Jarl refuses it with a clear message instead of skipping those issues. Existing loops and their files are unchanged.
- A range of issue numbers written in a free-text field, such as `1000-1002` in a "Found by" line, now counts every number the loop holds in it; before, its first number was lost whenever it looked like part of a date. A real date still counts for nothing.
- A new issue's file name no longer ends in a dash when its title is cut at 60 characters. Existing files keep their names.
- The follow-up count in `report` now counts only issue numbers the loop holds, so a date, a year or a version in a "Found by" line is never read as an issue.

## [6.1.0] - 2026-09-29

Jarl 6.1.0 lets one loop drive work across several repositories, keeps the loop out of your git history by default, and starts each new session from a single `resume`. Your agent reaches every command as an MCP tool, and the record gets firmer: an issue closes on recorded proof, and code on a fresh reviewer's approve. Jarl now shares one version number with the rest of the Yggdrasil family's core (Yggdrasil, Grain and Horde), so it moves from 0.1.0 straight to 6.1.0. Under that shared number a minor release can carry upgrade steps, and this one has a few.

### Before you upgrade

- Jarl runs on Node.js 22 or later (0.1.0 ran on Node 18). Install Node 22 first.
- New loops stay out of git: `init` has git ignore `.jarl/`, and worktrees of the same repository still find it. To carry a loop to another clone or machine, open it with `init "<goal>" --committed`, which keeps it on the branch as 0.1.0 did. Loops opened with 0.1.0 stay committed.
- `set <id> done` closes an issue once it has a `--ran`/`--saw` evidence row recorded since it last went in progress or was reopened; a free-text note, a ruling or a drop or defer reason does not count on its own. An approve holds until the next red round, reopen or restart. Record a row with `evidence <id> --ran "<command>" --saw "<output>"` before you close. Issues already done stay done.
- Every `review` names its reviewer with `--by <reviewer>`, and Jarl refuses an approve from anyone who worked the issue or its branch. An issue that records a branch or a merge closes on a fresh reviewer's approve, from someone who neither wrote the code nor runs the loop; the coordinator (`jarl`, `reeve`, `coordinator`, the loop's directory name, or a name on a `Coordinators:` line in `goal.md`) closes rulings and documents. Raise a fresh reviewer for every branch.
- The command line checks its input: it refuses an unknown flag or an extra argument with exit code 1, and for a flag it names the ones the command takes. A value starting with `--` belongs to the flag before it; a note or title starting with `--` goes after a bare `--`. `decide` takes slugs of letters, digits and `. _ -`, and `ask --issue` takes an existing issue. Adjust any call the tool refuses.
- `resume` takes over from the handoff and assembles the state live. `handoff write` succeeds and writes nothing, `handoff read` prints what `resume` prints and needs a loop, and `status` leaves out the handoff's age. Start sessions from `resume`.
- `report` prints "Found along the way" when you pass `--found`. Add the flag wherever you want that section.
- The journal's review line reads `NNN review approve · by <name> (<kind>) · <findings>`. Update anything that parses it.

### Upgrading from 0.1.0

1. Install Node.js 22 or later.
2. Update the plugin. In Claude Code: `/plugin marketplace update jarl-marketplace`, `/plugin install jarl@jarl-marketplace`, then `/reload-plugins`; the README covers Copilot, Codex and Cursor. A drop-in copy takes the whole `skills/jarl/` directory.
3. A loop opened with 0.1.0 carries on as a committed loop. On its first write, Jarl adds an ignore file and merge settings inside `.jarl/` and a merge driver to the repository's local git configuration. Commit the new `.jarl/` files with the loop.
4. Bring scripts and agent instructions that call the tool in line with the list above.
5. To have ratified rulings written into Yggdrasil's logs, use Yggdrasil 6.1.0 or later. With an older `yg`, Jarl prints the command to run by hand.

### Added

- One loop can drive work in several repositories. Name the repository root on the issue (`new --repo <path>` or `repo <id> <path>`) and its files carry that repository's name first (`tool/src/a.mjs`, or `app/app/x.mjs` when the repository holds a directory of its own name). `next`, `check`, `resume`, `report` and the other views follow the issue there.
- From any worktree of the repository, the tool finds the loop without `--root`.
- `resume` gives a new session everything in one read, from the goal and the rulings in force to the work in flight, the merge queue and CI. It writes nothing and needs no network unless you pass `--ci`.
- `init "<goal>" --permanent` keeps a loop after `close` as a record, and `mode permanent` turns a committed loop into one. `archive "<slug>"` puts a finished loop away so a new one can open in its place, and `set <id> deferred "<why>"` parks work that waits on someone.
- A committed loop merges cleanly when two branches carrying it meet, and stops with conflict markers when both changed the same ruling. `merge-driver flags` prints the settings for `git merge`.
- Fuller issues. `new --where --what --why --acceptance` and `body <id>` write the body, `after <id> <ids>` orders issues, `new --template <name>` starts from a template, and `--changelog "Added: …"` keeps the issue's changelog entry until `changelog <ids>` prints it at merge time. `evidence`, `review`, `set`, `tag` and `prio` take id lists such as `203-206`, all or nothing.
- Branches, merges and CI on the record: `set <ids> in-progress --branch <b>` leases a package of issues, `merged <ids> --sha <sha> --ci <state>` records a merge, `queue` shows the merge queue, and `tips` shows each repository's branches with their CI. None of them blocks a merge.
- `report` ends with loop metrics: cycle and lead time, rounds, reopenings, the share of fresh reviews, red CI after a merge, and follow-ups. A `Check: <command>` line in `goal.md` names the check that decides what lands.
- Rulings can supersede one another (`decide --supersedes`, `decisions --live`), and `ask --kind ratify` records a choice that waits for your word. `decide --area <type> --reach <n>` marks a ruling for every file of a type; `close` puts these to you in one batch and, in a repository with a Yggdrasil graph, writes each one you ratify into that type's decision log. Add `--rule <id>` to name one of the graph's rules, and your yes also ratifies that rule in Yggdrasil so it can stand enforced, for every type the rule reaches.
- `import <findings.json>` files one issue per research finding, once, and `sources` shows what was filed.
- An MCP server starts with the plugin. Every command is a tool with the same arguments, marked as writing or read-only, and the whole list costs an agent about 7,000 tokens. `JARL_ROOT`, if you set it, takes an absolute path.
- Profiles let a tool such as Horde run its work as Jarl loops: `init "<goal>" --profile <file>` sets statuses, fields and sections, and can hand scheduling, the done check, `close` and `archive` to that tool.
- A versioned library, `jarl-record/1`, lets a tool read and write a loop without the command line.
- JSON for dashboards: `status --by repo|tag|kind|prio`, more counts in `status --json`, one row per issue in `report --json`, and `waitsOn` and `after` as lists on every `next --json` row. The skill documents these shapes as stable.
- Jarl runs on Windows, checkouts with Windows line endings included, and Copilot and Codex can install it from a portable Agent Plugins 1.0 manifest.

### Changed

- `branches` without `--repo` covers every repository an open or in-progress issue names, and marks stale leases and branches ready to delete.
- A line in `goal.md`'s rules, or a ruling, can give standing permission to push the feature branch; the merger then pushes it after each green merge. Worker branches stay local.
- Where a helper agent cannot start agents of its own, the loop notices at the start and relays every spawn through files, second rounds included.

### Fixed

- Workers, reviewers and the merger can write at once: each write waits its turn behind a lock, so every evidence row, log line and issue number lands.
- Evidence grows line by line: a note, a drop reason and each `--ran`/`--saw` pair add a line of their own to what the issue already holds, text with `$&` or `$1` included.
- `check` counts a file an issue names relative to a subdirectory as in scope.
- The merger also removes the branch a worker started on when the platform created its worktree.
- Titles with `ł`, `ø`, `ß` and similar letters give readable file names: `gałęzi` becomes `galezi`.
- In a dev container handed the host's install path, the skill uses its own copy of the tool, or stops if there is none.

## [0.1.0] - 2026-09-13

### Added
- The `jarl` skill. Invoke `/jarl <goal>` on a feature branch and the agent becomes the director of that branch: everything anybody sees becomes an issue in a committed `.jarl/` directory, one worker per issue works in its own worktree, nothing merges without evidence the agent has reproduced itself, and the directory is removed by the last commit before the branch merges to main. Testing, stress and research sessions run on the same loop, with some workers producing issues while others take them down.
- One small tool, `jarl.mjs`, that every change of state goes through: file an issue, list and search by status, kind, tag, priority or text, change a status with its reason written to the journal in the same move, tag and prioritise, ask the user a question of one of four closed kinds (stop, stuck, lower with a named target, charter) rather than free text, record evidence — free text, or a repeatable checkable row naming the command and what it printed —, record a review verdict where "changes" must name a Critical or Important finding (Minor alone rides an approve instead of bouncing the branch), ask what can run in parallel right now, count red rounds and hand an issue to a fresh worker after three, check a worker's branch before merge (commits, files outside the declared scope, test files removed, assertions before and after), list worker branches with unmerged commits, file questions only the user can answer and turn their answers into rulings, write a handoff for the next session, produce the closing report, and close the loop; its worker guidance now steers a scratch copy over `git stash` for holding work aside, since the stash list is shared across every worktree of a repository, and never checks out a ref in the main checkout — the merger alone moves it, and now confirms each `done` actually landed before moving to the next branch; the loop now treats a merger's own report as the only signal it has stopped touching the main checkout, after a rewritten HEAD surfaced when that was assumed instead of confirmed — which refuses while anything is still open. Node, no dependencies.
- Three standing helpers the loop raises so the director's own context is spent on the client: a reeve that runs the loop day to day and reports back on four occasions only, a fresh reviewer per branch, and a merger that verifies and merges one branch at a time. Worker branches are named by issue and never leave the machine.
- Installable as a Claude Code plugin, a GitHub Copilot CLI plugin, a Codex CLI plugin and a Cursor plugin, or as a single file dropped into any agent's skill directory.
