## [Unreleased]

### Added
- An issue can be filed whole: `new` takes `--where`, `--what`, `--why` and `--acceptance` (one checkable line each, repeatable), and `body <id>` sets or replaces them later. Nothing is required, and older issues read as before. `next` marks an issue with no acceptance line, `status` lists the in-progress ones without one, `set done` notes it without refusing, and `review` prints the acceptance its verdict is given against.
- `import <findings.json>` files one issue per research finding, with a new **Source:** field `<report dir>#<finding id>`, and never files the same finding twice: a re-run skips every finding an issue already carries, and a finding named by an older issue without Source is reported (`--adopt` links it) instead of filed again. It reads the flat, the angles (`surviving`) and the `results`/`kept` shapes with a documented mapping; flags override kind, priority, tier, tags, repository and who found it; `--dry-run` and `--only` take a look or a part first. `sources` shows, per report, the findings, the issues filed from them and their status, and the unfiled ones. `new --source` and `source <id>` record the finding on an issue filed by hand.
- `ask --kind ratify` records a choice made under the user's mandate that waits for their word. It blocks nothing, `status` lists it apart from the questions (`to ratify N`), the handoff has its own heading for it, and its answer is written into the issue it names.
- An issue can wait on others: `after <id> <ids>` or `new --after` records **After:**. `next` does not offer it until those are done or dropped, and `status` counts it as waiting instead of in flight. `decide … --settles <ids>` writes a ruling into the evidence of the issues it settles. An answer to a question asked with `--issue` is written there too.
- `next --json` rows always carry `waitsOn` (files held by work in progress) and `after` (unsettled After issues) as lists, empty when nothing holds the issue; a ready row may carry `noAcceptance: true`. `status --json` adds `waiting`, `waitingIds`, `inFlight`, `ready`, `noAcceptance`, `ratify` and `toRatify`; `open` and `in-progress` still count those statuses.
- `evidence`, `review`, `set`, `tag` and `prio` take several issues at once, as one comma list with ranges (`12,13,14` or `203-206,209`). Every issue and every precondition is checked first, so the call changes all of them or none, and each issue still gets its own log line. Closing a package of issues merged together takes four calls instead of four per issue.
- A package of issues on one branch is a first-class shape. `set <ids> in-progress --branch <b> --worker <name> --worktree <path>` writes one lease on every issue: **Branch:**, **Worker:**, **Worktree:** and **Since:** (Since is written on every move to in-progress). Leaving in-progress removes Worker, Worktree and Since and keeps Branch. `check --branch <b>` with no id bounds the diff by the union of the Files of every issue on that branch, so a shared branch passes in one call. `branches` prints the issues on each branch (`jarl/163-packages → 163, 164`), marks a lease STALE when its worktree or branch is gone or it has been idle longer than `--stale-hours` (default 6), and marks a branch DONE → delete once its issues are settled, its tip is in the base (or in every merge sha its issues record) and its worktree is clean; otherwise it says `DONE (merged by record, branch not in base) — verify` or `DONE (worktree dirty)`. With no `--repo` it also reads every repository where an issue records a Branch. `status` lists the stale leases. Nothing expires and nothing is taken over.
- `merged <ids> --sha <sha> [--ci pending|green|red|none] [--repo <path>]` records the merge as **Merged:** and **CI:** fields with a log line, and `merged <ids> --ci <state>` moves the CI state later. `status` counts `merged, CI pending N` and `CI red N`, `report` prints the sha per done issue, and `set done` notes on stderr, without refusing, an issue whose CI is not green yet.
- In a committed or permanent loop, `status`, `handoff write`, `handoff read` and `close` name how many loop files git has not committed. Nothing is said in the default mode or outside a git repository.
- `handoff read` computes in-flight work, the waits, the open questions and the ratify items from the issues and asks, and keeps only the summary and next from the file. It prints the handoff's age, `STALE by 3d` when the loop moved on after it, how many log lines and issues changed since, and which recorded heads moved. `status` prints the handoff's age next to the last activity.
- `tips` is a read-only view of where each repository stands: for the loop's own repository and every one an open, in-progress or recently merged issue names, the tip of each worker branch in flight, the release branch and `main`, ahead/behind their upstream as last fetched, and, when `gh` is on PATH, the CI of that exact commit for a tip that was pushed (green, red, pending or none); a tip its remote does not hold reads `not pushed`. Without `gh` the CI is left out. It fetches nothing, writes nothing and gates nothing. `--json` gives the same.
- `decide --supersedes <slug>` marks an earlier ruling **Superseded by:** in place, and `decide --by <who>` records who ruled (`owner` unless given). `decisions [--live]` lists the rulings with who ruled and what superseded them; `--live` lists only those still in force, and the boot reads that.
- An issue may name several repositories: `--repo ../tool,../lib` on `new`, `import` and `repo`. Each file starts with the name of its repository, `next` keeps each (repository, path) pair apart, `check` on such an issue takes `--repo` and bounds the diff by the files declared there, and `branches`, leases, `merged` and the handoff read every repository named.
- `review --by <reviewer>` records who reviewed and its kind: fresh, coordinator (`--by jarl`) or self (the issue's worker). `status` and `report` print who reviewed the done work (`fresh a · coordinator b · self c · unrecorded d`).

### Fixed
- Text containing `$'`, `` $` ``, `$&` or `$1` written into an issue (a note, a body section) is written as it is. Before, `evidence` treated it as a replacement pattern and could duplicate the issue's sections.
- Parallel calls no longer lose each other's writes. Before, workers, reviewers and the merger writing at the same moment could drop evidence rows and log lines, fail with "no such issue" on a half-written file, or file two issues under the same number. Every command that writes now waits its turn behind a lock, taken over automatically when the process holding it is gone, and every file is replaced whole.
- A value that starts with `--` is kept as the value of the flag before it: `--ran "--help"` records the row instead of printing the usage and exiting with success, and `--saw "--- FAIL"` works. A note or title that itself starts with `--` goes after a bare `--`, and `--flag=value` is accepted.
- A misspelt or unknown flag is refused with the list of flags the command takes, and so are extra arguments, instead of being silently ignored.

### Changed
- `set done` needs at least one `--ran`/`--saw` evidence row recorded after the issue last went in progress (or was reopened; for an issue that never went in progress, after it was filed). A free-text note never satisfies it alone, so a note written at filing time no longer closes an issue. An approve is spent by a round, by any move out of done, by a reopen (done or in progress back to open) and by a restart (in progress again after deferred, for one). Issues already done stay done; only the next move to done is checked. An issue the journal has no filing or status line for needs a `--ran`/`--saw` row in its Evidence.
- `review` needs `--by <reviewer>` on every verdict, and an approve by the issue's own worker (its **Worker:**, or the worker of its last lease) is refused: a self-approve is not a review. A `changes` verdict by the worker is recorded. The log line now reads `NNN review approve · by <name> (<kind>) · <findings>`.
- `decide` refuses a slug outside letters, digits and `. _ -`, and compares slugs as strings. Before, a slug with a regex character could crash the call, and `q.r` was refused as a duplicate of `qxr`. A ruling line starting with `#` is escaped, so it cannot open a section of its own.
- `report` groups the done issues per repository when they span several, and lists an issue that names two under each. The "Found along the way" section is now opt-in with `report --found`.
- `ask --issue <id>` refuses an issue that does not exist, instead of recording a question about it.
- `set done` no longer counts a `Ruling …`, `Dropped:` or `Deferred:` line in Evidence as evidence of the work: a ruling written into an issue, or the reason of an earlier drop, does not by itself let it close.
- `init --committed "<goal>"` and `init --permanent "<goal>"` (the flag before the goal) now open the loop. Before, the flag took the goal as its value and the command refused.
- A committed or permanent loop now carries a small ignore file that keeps only the write lock and half-written temporary files out of git, so committing the loop while a call runs never commits them. A committed loop opened with an earlier version gets the file on its next write. The loop itself is still committed, and the mode is unchanged.

## [0.2.0] - 2026-09-25

### Added
- A portable Agent Plugins 1.0 manifest, `plugin.json` at the repository root, which Copilot and Codex read before any host-specific manifest. The host manifests stay for Claude Code, Cursor and older Copilot and Codex, with the same name, version and description.
- `archive "<slug>"` puts the current loop away under `.jarl/archive/<yyyy.mm.dd>-<slug>/` so a new one can be opened in the same place. Everything moves except the archive and the mode markers, so `init` then opens the next loop in the same mode (and refuses a flag that contradicts it). Before, a finished loop had to be deleted or moved by hand, because `init` refused any existing `.jarl/`.
- `status` now also prints the loop's goal, when it was opened and when anything last happened in it, and SKILL.md tells the agent to ask once, at a session's first contact with an existing loop, whether to continue it or archive it.
- `repo <id> --clear` removes an issue's **Repo:** field again.
- Run from a worktree of a repository whose main checkout holds the loop, the tool now finds that loop by itself, so a worker or reviewer no longer has to pass `--root <main checkout>` to be understood. Before, the same call answered as if there were no loop at all. `--root` still wins when given, and a loop that lives in another repository is still reached with it.
- An issue can be deferred: `set <id> deferred "<why>"` for work that waits on someone, as opposed to work that is gone. The default list leaves it out (`list --status deferred` or `--all` shows it), `status` and `report` count it apart from dropped, and `close` names what it leaves waiting instead of treating it as finished or abandoned.
- A loop can now be opened as a permanent record instead of tied to a feature branch: open it with `--permanent` and it lives for good wherever you point it — a repository that keeps one loop per release as that release's record, say, directing work in other repositories over time. Closing it still refuses while anything is open or in progress, exactly as before; once everything is settled, it no longer deletes the loop, it stays as the record.
- A loop can now keep its issues in one repository while its workers change another. Name the other repository when you file an issue (or later, on the issue), or on the command itself, and checking a worker's branch before merge looks there: its commits, files and test assertions, compared against that repository's own current branch. Listing worker branches can look there too, and the handoff between sessions records where that repository stands. A relative path means the same from every checkout the loop's roles work in. Loops that work in a single repository behave exactly as before.
- In a loop that spans repositories, an issue that names a repository lists its files with that repository's name first, as in `tool/src/a.mjs`. Picking what can run in parallel then tells the same path in two repositories apart instead of making one issue wait for the other, while two issues on one file in the same repository still wait, and checking a worker's branch counts its changes as inside the files the issue declared rather than flagging every one as outside.
- A loop opened before the permanent mode existed, or opened as committed, can now switch to it in place: `mode permanent` marks it as a record, exactly as opening one with `--permanent` would, with a log line to show for it. It refuses a loop that is still out of git — a permanent record must be committed first — and refuses again on a loop already in the permanent mode.

### Changed
- `branches` without `--repo` now lists worker branches in the loop's own repository and in every repository an open or in-progress issue names, each row naming its repository. Before, a loop whose issues pointed at other repositories showed none of its workers' branches at boot unless you named the repository yourself.
- A loop can carry the user's standing permission to push its feature branch: written in `goal.md` or as a ruling, and then the merger's brief tells it to push the feature branch after a green merge. Worker branches are still never pushed, and without that line a push remains the user's word each time.
- The loop's files now stay out of git by default: opening a loop tells git to ignore them, so they no longer appear in your branch's history, diffs or merges, and the branch carries nothing of the loop to main. Because git ignores the loop, it exists only in the checkout it was opened in: a worktree does not see it, so workers, reviewers and the merger reach it by passing that main checkout to the tool (`--root`), and another clone or machine does not have it. The merger no longer commits it. To keep the loop in the repository's history instead, open it with `--committed`: it is then committed with the work and removed before the branch merges to main, as before. Loops already open are left as they are.
- The reeve now checks, at boot, whether it can raise agents of its own before assuming it can; if not, it tells the jarl and the file-relay fallback takes over for the rest of the loop.
- The file-relay fallback now also covers resuming a worker or a merger for a second round, not only the first spawn.

### Fixed
- The README described `--committed` as the way to keep the loop as a permanent record, although a committed loop is removed before the branch merges, and said an open loop keeps its mode. It now describes the three modes as the tool has them: out of git by default, `--committed` to travel with the branch, `--permanent` to keep the loop after `close`, plus `mode permanent` and `archive`. The repository's CLAUDE.md no longer says every session opens a committed loop.
- `SKILL.md` now says what to do when the tool's path does not exist where the agent runs, as when VS Code attached to a dev container hands it the host's install path: take `scripts/jarl.mjs` beside the `SKILL.md` it read, or find the copy this environment has with one `find`, use that absolute path for the session and hand it to every role, and stop if there is none.
- In a loop that spans repositories, three cases of the repository name in **Files:** were read wrongly and silently. `check --repo` on an issue with no **Repo:** field now strips the name as the field does; in a repository that has a directory of its own name, `app/x.mjs` is no longer shortened to `x.mjs` (the prefix is required there, `app/app/x.mjs`), so `next` no longer misses a collision; and a repository spelled through a symlink or in another case is one repository, not two.
- A repository named for an issue (`--repo`, or the **Repo:** field) must now be the repository's root: a subdirectory of it is refused with the root to give instead. Before, its paths were read from the wrong place, so `check` could miss a removed test. The worker's brief also says that with a **Repo:** field the feature branch and worktree are in that repository.
- The merger now removes the branch a worker began on as well as `jarl/NNN-slug` when the two differ, and the worker's brief tells it to rename the platform's branch (`git branch -m`) instead of creating a second one. Before, a worker in a platform-made worktree left its original branch behind after every merge.
- Dropping an issue no longer wipes what was already written under its Evidence. The reason is added as one more line, and `report` still prints only the reason for a dropped issue.
- An issue title with a letter Unicode does not decompose, such as the Polish `ł`, now gives a readable file name: `gałęzi` becomes `galezi`, not `ga-ezi`. The same goes for `ø`, `ß`, `đ`, `æ` and a few others. Existing files are not renamed.
- `check` no longer flags an in-scope change as outside its declared files when an issue names a file relative to a subdirectory (a plugin's own skill body, say) rather than the repository root.
- Free-text evidence is now added after what the issue already holds. Before, it replaced the whole evidence section, so the merger's note after a merge erased the proof the worker had recorded.
- Several `--ran`/`--saw` pairs in one `evidence` call now become one row each, instead of one unreadable row with every command and every result joined by commas. A `--ran` or `--saw` given without a value is refused instead of written down.

## [0.1.0] - 2026-09-13

### Added
- The `jarl` skill. Invoke `/jarl <goal>` on a feature branch and the agent becomes the director of that branch: everything anybody sees becomes an issue in a committed `.jarl/` directory, one worker per issue works in its own worktree, nothing merges without evidence the agent has reproduced itself, and the directory is removed by the last commit before the branch merges to main. Testing, stress and research sessions run on the same loop, with some workers producing issues while others take them down.
- One small tool, `jarl.mjs`, that every change of state goes through: file an issue, list and search by status, kind, tag, priority or text, change a status with its reason written to the journal in the same move, tag and prioritise, ask the user a question of one of four closed kinds (stop, stuck, lower with a named target, charter) rather than free text, record evidence — free text, or a repeatable checkable row naming the command and what it printed —, record a review verdict where "changes" must name a Critical or Important finding (Minor alone rides an approve instead of bouncing the branch), ask what can run in parallel right now, count red rounds and hand an issue to a fresh worker after three, check a worker's branch before merge (commits, files outside the declared scope, test files removed, assertions before and after), list worker branches with unmerged commits, file questions only the user can answer and turn their answers into rulings, write a handoff for the next session, produce the closing report, and close the loop; its worker guidance now steers a scratch copy over `git stash` for holding work aside, since the stash list is shared across every worktree of a repository, and never checks out a ref in the main checkout — the merger alone moves it, and now confirms each `done` actually landed before moving to the next branch; the loop now treats a merger's own report as the only signal it has stopped touching the main checkout, after a rewritten HEAD surfaced when that was assumed instead of confirmed — which refuses while anything is still open. Node, no dependencies.
- Three standing helpers the loop raises so the director's own context is spent on the client: a reeve that runs the loop day to day and reports back on four occasions only, a fresh reviewer per branch, and a merger that verifies and merges one branch at a time. Worker branches are named by issue and never leave the machine.
- Installable as a Claude Code plugin, a GitHub Copilot CLI plugin, a Codex CLI plugin and a Cursor plugin, or as a single file dropped into any agent's skill directory.
